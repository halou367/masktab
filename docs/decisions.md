# 实现决定与踩过的坑

每条写清：结论、原因、证据（在哪验证的）、影响。新的放在对应小节末尾。
“实测”如果没有另外说明，指无头 Linux（容器里，内核 `--headless=new`）。Windows 的证据只来自 CI 的冒烟测试。

## 内核

### K-1 内核固定在 fingerprint-chromium 148.0.7778.215，不用 150.0.7871.186

- **现象**：150.0.7871.186 开启 `--fingerprint=<种子>` 后，页面一做画布读回（`getImageData`，上游还报告了 `toDataURL`、WebGL `readPixels`），
  渲染进程就崩溃。在无头模式里表现为调试端口上的求值永远不返回，所以一开始被误认为“卡死”。
- **证据**：
  - 本项目实测：`--fingerprint=1000` 下，32×32 红色画布第一次 `getImageData` 必崩；不带 `--fingerprint` 或加 `--disable-spoofing=canvas` 不崩。
    “先读一次纯黑画布再读别的”能让一部分情况不崩，但不可靠（同一套代码有时崩有时不崩），不能当修复手段。
  - 上游 issue #94（Linux，SIGSEGV）、#95、#104（Windows x64，同一版本）描述一致，都说 148.0.7778.215 没有这个问题。
  - 148.0.7778.215 实测：连续 300 次 2D 读回正常；不同种子哈希不同、同种子重启后不变。
- **影响**：内核是 2026 年 6 月的 Chromium 148，比 150 少几个月的安全修复。上游修好后应尽快升级。
- **升级办法**：改 `internal/kernel/fetch.go` 的 `KernelVersion`，跑 `scripts/smoke.mjs`。其中“内核原生：开启指纹后 300 次画布读回不崩溃”
  和“伪装实例里连续 300 次画布读回不崩溃”两项就是为这个问题设的，不过就别升。
- `kernel.Find` 在自动下载目录（`data/kernel/fingerprint-chromium/`）里只认当前固定的版本，换版本后会自动重新下载。

### K-2 内核再次启动时，伴随扩展后台可能起不来；做了自愈

- **现象**：一个实例被强杀多次后，它的资料目录里 Service Worker 注册会卡死：扩展页面能打开，但后台永远不启动，
  `navigator.serviceWorker.getRegistrations()` 都不返回。删掉 `profiles/<id>/Default/Service Worker` 目录后恢复。
- **做法**（`internal/core/launch.go`）：实例运行超过 45 秒而伴随扩展后台一次都没连上核心服务，退出时在资料目录里放标记文件 `.repair-sw`；
  下次启动前看到标记就删掉 `Default/Service Worker`。代价是该实例里网站自己的 Service Worker 要重新注册（下次访问时自动完成）。

## 伴随扩展

### K-3 工具栏图标不经过画布

- 指纹内核会给画布读回加噪声，图标会花；150 版还会崩（K-1）。而 `chrome.action.setIcon({path})` 内部也是画布读回，同样受影响。
- **做法**：国旗和状态图标预先转成 32×32 原始 RGBA 字节，gzip 后放在 `companion/ext/assets/rgba/`（254 个文件，共约 160 KB）。
  后台用 `DecompressionStream` 解开，直接 `new ImageData(...)` 交给 `setIcon({imageData})`，底部 4 像素画成实例颜色。
- 重新生成这些文件：从 `assets/flags/*.png` 缩放到 32×32（保持比例、居中、透明底）导出 RGBA 再 gzip。当时用的是 Pillow，脚本没有入库。

### K-4 伴随扩展的版本号跟着文件内容走

- 内核只在扩展**版本号变化**时才重新安装后台脚本。版本号不变，即使文件改了，资料目录里缓存的还是旧脚本。
- **做法**：`companion.Version()` 返回 `0.1.<a>.<b>`，后两段取自全部扩展文件内容的 SHA-256。启动实例释放扩展副本时把它写进 `manifest.json`。
  源码里的 `manifest.json` 保持 `"version": "0.1.0"` 作为占位，**不要改这一行的写法**（`writeCompanion` 按字符串替换）。

### K-5 停止实例先让伴随扩展关窗口，再结束进程

- 直接结束进程会丢掉最近约 30 秒内写入的 Cookie（内核每 30 秒落盘一次；实测无头 Linux 下 SIGTERM 也不落盘）。
- **做法**（`App.Stop`）：先发 `close` 事件，伴随扩展后台收到后 `chrome.windows.remove` 全部窗口，等 4 秒；没退出再 `taskkill`（Linux 是 SIGTERM），
  8 秒后强杀。
- **已知限制**：无头模式下关掉全部窗口后内核不会自己退出，所以无头测试里总是走到结束进程，刚写入的 Cookie 会丢。
  这一项要在有界面的 Windows 上才算数——CI 的 Windows 冒烟测试用 `--visible` 跑，结果见 `docs/PROGRESS.md`。
- 伴随扩展后台刚被唤醒时从核心服务的当前事件序号开始听，不重放旧事件。否则旧的 `close` 会把刚启动的实例关掉。

### K-6 伴随扩展是纯 JS，没有构建步骤（偏离计划 D4）

- 计划 D4 写的是 TypeScript + 打包。实际界面很小（弹出面板、管理页、新标签页），纯 JS 模块足够，少一条工具链，也更符合“轻”。
- 影响：没有类型检查。CI 里目前也没有对 JS 做静态检查，只有冒烟测试覆盖。要加的话用 `node --check` 逐个文件过一遍即可。
- 扩展 ID 固定为 `doepfdknoapkdegjpopaicigcdnhlifp`，由 `manifest.json` 的 `key` 决定，单元测试会校验 `companion.ID` 与 `key` 一致。

### K-7 界面状态靠长轮询

- 后台对 `/api/events?since=<序号>` 做长轮询，每次返回后刷新图标、角标、悬停文字；另有 30 秒闹钟兜底把后台叫醒；
  任何扩展页面打开时也会发一条 `wake` 消息。

## 界面（Windows 上看到的）

### U-1 新标签页用 `--custom-ntp`，不用扩展清单的 `chrome_url_overrides`

- 用 `chrome_url_overrides` 接管新标签页时，内核第一次打开新标签页会弹“Did you mean to change this page?”，默认按钮是“Change it back”，
  点了它伴随扩展就被停用，整个实例的面板、状态、快捷键全没了。页面底部还会多一条扩展署名栏。（Windows CI 截图里看到的。）
- 这个“已确认”状态存在 `extensions.settings.<扩展ID>.ack_ntp_bubble`，属于受保护偏好，不能从外部预先写入（见 U-2）。
- **做法**：清单里不声明 `chrome_url_overrides`；启动内核时加 `--custom-ntp=chrome-extension://<伴随扩展ID>/newtab.html`
  （ungoogled-chromium 系内核自带的参数，fingerprint-chromium 148 实测支持扩展地址）。
- 代价：换成不支持 `--custom-ntp` 的内核时，新标签页会是内核自带的那个。

### U-2 不要从外部改内核的“受保护偏好”

- Windows 上内核对一批偏好做完整性校验，从外部改了会被判为篡改并**整项重置**，重置记录在偏好文件的 `prefs.tracked_preferences_reset` 里。
  CI 导出的文件显示被重置过的有：`extensions.settings`、`extensions.ui.developer_mode`、`session.restore_on_startup`。
  `extensions.settings` 被重置意味着所有扩展的设置和授权都会丢，所以这条必须遵守。
- 同一类的还有主页、启动页、默认搜索引擎、固定标签页等。Linux 上不校验，所以这个问题只会在 Windows 上出现。
- **做法**：`prepareProfile` 只写普通偏好（实例名、关闭内置密码管理、退出状态、工具栏固定的扩展、WebRTC 策略、语言）。
  恢复标签页靠 `--restore-last-session`；默认搜索靠一个单独的小扩展；解包扩展不需要开发者模式也能加载（Windows CI 实测）。
- 想知道内核把某个设置存在哪：冒烟测试的 `dumpPrefs()` 会把实例的 `Preferences` 和 `Secure Preferences` 拷进截图目录；
  `--click x,y` 可以在截图后点一下屏幕上的按钮，再对比前后两份文件。`ack_ntp_bubble` 这个键名就是这样确认的。

- **补充（2026-11-17，需求方：“MaskTab 默认不在无痕模式下启用，我开了，插件就关了，又要我开开发者模式，再开插件”）**：
  上面那句“解包扩展不需要开发者模式也能加载”只对了一半。内核有一项功能 `ExtensionDisableUnsupportedDeveloper`：没开开发者模式时停用从文件夹加载的扩展。
  启动时它不查，**扩展一重新加载就查**；在 `chrome://extensions` 里拨一下“在无痕模式下启用”就会重新加载一次，于是扩展被停用（原因 `unsupportedDeveloperExtension`），重开内核也好不了。
  - 做法：启动参数加 `--disable-features=ExtensionDisableUnsupportedDeveloper`（`internal/kernel/kernel.go` 的 `commonArgs`）。已经被这样停用的，带上参数重开就自己恢复。
    内核只认最后一个 `--disable-features`，以后再关别的功能要写进同一个参数。
  - 不做的：预先写好开发者模式 / “无痕启用”。在需求方的 Windows 上试了三种写法（新用户目录预写、改 `Secure Preferences`、连校验码一起删），内核全部重置——就是这一条 U-2。
    所以伴随扩展**默认仍然不在无痕窗口里**，要用户自己拨一下开关（现在拨了不会出事）。无痕窗口里代理、指纹、WebRTC 策略照常生效（都是启动参数，不靠扩展）。
  - 证据：内核 148.0.7778.215，Linux 沙箱和需求方的 Windows 各跑一遍（不带参数：拨开关 → `DISABLED`；带参数：一直 `ENABLED`、重开还在；已停用的带参数重开 → 恢复）。
    需求方机器的开发版上对真的实例 #1 拨了伴随扩展和“默认搜索”两个扩展的开关，都还开着。冒烟每次都测（`scripts/ext-reload-e2e.mjs` 末尾三项），单元测试 `TestArgs` 守住参数。
  - 顺带看到、没处理：需求方机器的实例里列着“迅雷下载支持”“IDM Integration Module”两个扩展（装在系统里、所有 Chromium 都会被塞一份的那种），都是停用状态。

### U-3 启动提示条与新标签页署名栏

- **提示条**（已解决，2026-11-13）：每次启动，第一个标签页上有一条
  “您使用的是不受支持的命令行标记：--host-resolver-rules=MAP * ~NOTFOUND , EXCLUDE 127.0.0.1。稳定性和安全性会有所下降。”
  - 这个参数让内核自己一条 DNS 都不发，是防 DNS 泄漏的兜底，**不能去掉**：走 SOCKS5 时网页请求的域名由代理解析，
    但 WebRTC 解析 STUN / TURN 服务器的域名、DNS 预取这些旁路仍会在本机解析，泄漏检测站正是靠这类旁路看到真实的 DNS 出口。
  - 内核源码（`chrome/browser/ui/startup/infobar_utils.cc`、`bad_flags_prompt.cc`，148.0.7778.215）里，
    `--host-resolver-rules` 在“危险参数”名单的第一条；不出提示只有两条路：
    企业策略 `CommandLineFlagSecurityWarningsEnabled`（要写注册表，会影响本机其他 Chromium，并且菜单里多一句“由贵单位管理”），
    或者启动参数带 `--test-type`。选了后者，只在带 `--host-resolver-rules` 时一起加。
  - `--test-type` 的其他影响（逐个查过同一版源码里用到它的地方）：
    不建任务栏跳转列表；已安装的网页应用不自动更新快捷方式；扩展自己的上下文里多一个 `chrome.test`；
    内核升级后不给扩展补发 `onInstalled(chrome_update)`；带后台页的内置组件扩展不加载
    （这一版非 Google 品牌的构建里本来就没有：Hangouts 组件在 ungoogled 里关了，联网语音合成只有 Google 品牌才有）。
    没有发现网页能观察到的差别；冒烟测试里两个实例的指纹、扩展后台、重启恢复都照常。
  - 同时不再出现的还有：缺少 Google API 密钥、系统过旧、默认浏览器这几种启动提示条（原本也用不上）。
- **新标签页底部的署名栏**（“MaskTab”链接和“Customize Chromium”按钮）：改用 `--custom-ntp` 后仍然在。
  试过在偏好里写 `ntp.footer_visible=false` 和 `ntp.footer.extension_attribution_enabled=false`，没有效果，已经删掉。用户可以在“Customize Chromium”里手动关。

## 代理

### P-1 mihomo 的编排方式

- 每个实例一个本地监听 `in-<实例ID前8位>`，对应一个策略组 `g-<同>`，成员是 `[REJECT, 该实例可选的节点…, DIRECT]`。
  选节点 = 通过 mihomo 的控制接口切换策略组当前项，不重写配置文件（实测切换节点后 `core/config.yaml` 不变）。
- 代理名：通用订阅节点 `s-<订阅8位>-<节点键8位>`；edgetunnel 实例专属节点 `n-<实例8位>`；优选地址 `a-<地址8位>`。
- 节点键 = `sha1(类型|服务器|端口|凭据|host|ws 路径)`。
- 另有一个独立的探测监听，用来测出口 IP，它不受“切断”影响。
- **切断**：代理开着但不可用、出口时区变了需要重启等情况，策略组切到 `REJECT`。任何情况下都不自动切到 `DIRECT`（硬规则 R-1）。
  实测：切断后页面得到 `chrome-error://chromewebdata/`。
- mihomo 意外退出后 1 秒自动重启，并重新选回各实例原来的节点（实测）。

### P-2 edgetunnel 的识别与路径

- 识别规则（2026-11-13 按真实 edgetunnel 的输出改过）：至少 2 个节点；全部是同一种协议（vless 或 trojan）+ ws、凭据相同；
  Host 的种类数 ×2 不超过节点数（通配 Host 按后缀归并）。**路径允许各不相同**：edgetunnel 开“随机路径”后每个节点路径都不一样，
  旧规则要求路径相同，会把它误判成通用订阅。模板优先取带 TLS 的节点。
- 路径改写（实测生成结果）：ProxyIP 出口 `/?proxyip=<值>&ed=2560`；SOCKS5 出口 `/socks5://u:p@1.2.3.4:1080?ed=2560`；没有出口保持 `/?ed=2560`。
- 优选 IP“同出口”模式：直接把出口地址当作连接的服务器。出口当入口不可用时显示“出口探测失败”并切断，不回落。
- 验证方式：本地用 wrangler 跑真实的 edgetunnel `_worker.js`（2026-11-10 版），前面放一个 TLS 终结，订阅走它自己的 `/sub`。
  默认配置、0-RTT、随机路径、ECH、三者同开、经 subconverter 的 Clash YAML 都测过。用户自己的线上订阅仍然没有测过（V5）。

### P-4 ECH

- edgetunnel 链接里的写法是 `ech=<查询名>+<DoH 地址>`（如 `cloudflare-ech.com+https://dns.alidns.com/dns-query`）。
  旧代码只生成 `ech-opts: {enable: true}`，mihomo 就去查节点 SNI 自己的 HTTPS 记录，查不到，报
  `resolve ECH config error: no ECH config found in DNS records`，表现为**全部节点测速超时、实例打不开**。
- 现在：`ech-opts` 带上 `query-server-name`；长 Base64 当作 `config`；没转义的 `+`（会被解析成空格）也认。
- 只要有出站用了 ECH，配置里就加 `dns` 段：默认用系统 DNS，只把 ECH 查询名用 `nameserver-policy` 指到国内可达的 DoH
  （alidns、doh.pub）。实测 mihomo 1.19.34 能据此取到 Cloudflare 的 ECH 配置。
- **自动回退**：一轮测速后如果全部节点都不通且原因是 ECH，把该订阅标记为“不使用 ECH”（`echOff`）再测一遍。
  Cloudflare 上的服务端同时接受不带 ECH 的连接，所以回退后能用。面板“更多”里可以手动开关。
- 本地验证的限度：本地的 TLS 终结不支持 ECH，所以“带 ECH 连通”演示不了；验证到的是 ECH 配置能取到、以及回退后连通。

### P-5 测速与节点列表

- **全部订阅的全部节点都写进 mihomo 配置**（edgetunnel 每个优选 IP 一条不带出口参数的出站）。旧做法只写“正在运行的实例用到的节点”，
  结果是没开伪装实例时通用订阅的节点全部测成超时。
- 另开 4 条**测速通道**（`in-scan<i>` + `g-scan<i>`），测出口 IP 时把通道切到要测的节点再发真实请求。
  延迟用 mihomo 的延迟接口并发测；出口 IP 经测速通道访问 `checkip.amazonaws.com` 等，再查归属地。结果存 `state/scan.json`，12 小时内不重复查出口。
- **失败原因**取自 mihomo 日志里该策略组最近一次拨号错误，翻译成一句话（连接被拒绝 / 连接超时 / 握手被中断 / 证书校验失败 / 服务端拒绝 / ECH…）。
- 配置重载会把所有策略组重置。用一个重载计数识别“测试期间发生过重载”，发生过就重测一次，避免把节点误判成不通。
- **自动选节点**（`proxy.auto`，新实例默认开）：启动时或探测失败时，当前节点可用就不动（出口稳定优先于速度）；不可用才测一遍并换成延迟最低的，
  最多换两次。手动点选某个节点会关闭自动。自动只在“代理开着”的前提下换节点，永远不会切到直连（R-1 不变）。
- 界面上一张列表：地址、备注 · Host、出口 IP 与归属地、延迟。edgetunnel 的“节点”就是优选 IP；ProxyIP、Host、自定义地址、ECH 开关收在“更多”里。

### P-6 入口、反代与"出口地区"（2026-11-13，依据真实订阅实测）

实测结论（需求方的 edgetunnel 订阅，20 条链接只有地址不同）：

- 普通网站从 Worker 所在的 Cloudflare 机房出去（`104.28.x`），**每次请求 IP 都可能变**，入口地址只决定机房在哪个国家。
- Cloudflare 上的网站从反代（ProxyIP）自己的固定地址出去，与入口无关；不指定时用服务端默认值，国家可能与入口不同。
- 所以一条线路固有两个出口。只有 SOCKS5 / HTTP 全局出口或"通用 ProxyIP"能让所有网站看到同一个 IP。

据此的做法：

- 入口有三个来源：订阅里的地址、自己加的地址、反代列表里每个解析出的 IP（它们大多也能当入口）。
- 反代候选有两个来源：反代列表，以及入口里不属于 Cloudflare 网段的地址（标"入口"）。`主机:端口` 相同即同一台机器。
- 测速分三步：延迟 → 每个入口的两路出口 → 经一条可用入口测每个反代的出口。结果存 `state/scan.json`。（edgetunnel 订阅已改为直接探测，见 P-7。）
- 面板的主控件是**出口地区**：在该地区里选最快的可用入口，再配一个同国家的反代。
  选不出时线路保持不变并说明原因，不退到别的地区。手动选入口或反代即关闭自动。
- 订阅每次返回的地址都不同：新结果里没有的地址标"旧"，在用的或还通的保留（每个出口国家最多 6 个），其余删掉。
- **延迟口径**：配置开 `unified-delay`，显示的是连接建好之后的一次往返。
  之前显示的是首次请求耗时（TCP + TLS + WebSocket 握手再加目标站 TLS，约 5 到 6 个往返），与别处的 tcping 数字差几倍。
- 计划里的"优选 IP 同出口 / 自选"药丸开关取消：反代 IP 直接出现在入口列表里，效果相同，少一个概念。

### P-7 直接探测、优选与反代的识别、测下载（2026-11-13，参照 edgetunnel 面板的"在线优选"）

第三轮反馈：国旗不显示、"1 / 58 可用"、反代列表不全、测速慢且只测了入口。原因是同一个：
出口信息全靠"经代理内核一条一条建隧道"去测，慢，而且隧道一旦建不起来，国旗、延迟、出口就全是空的。

edgetunnel 的"在线优选"是这样做的：浏览器直接连被测地址，请求一个返回 `ip / country / colo` 的小接口；
返回的 `ip` 是自己的公网 IP，说明连的是 Cloudflare 官方 IP（优选）；否则是反代，`country` 是反代机器所在国家。
测下载是 `__down?bytes=…`，流式读，每 250 毫秒报一次速率。

据此的做法（`internal/cfprobe`、`internal/core/fastscan.go`）：

- edgetunnel 订阅的地址**不经代理内核，本机直接连**，请求 Cloudflare 自带的 `/cdn-cgi/trace`。一次请求得到：
  通不通、TCP 握手耗时、一次往返的延迟、落在哪个机房（= 普通网站的出口国家）、Cloudflare 看到的来源 IP（= 把它当反代用时的出口）。
  32 路并发，单个 4 秒超时，结果随测随显示；没有运行中的实例、代理内核没起来也能测。
- **优选还是反代自动识别**：地址在 Cloudflare 网段内，或 trace 返回的来源 IP 等于本机公网 IP → 优选（只能当入口）；
  否则 → 反代（入口和反代都能当）。导入时不用区分。
- 每个 `地址:端口` 写两条记录：作为入口的、作为反代的。所以反代列表 = 所有识别为反代的地址，不再依赖"经某条入口去测"。
- 探测用的站点名：`/cdn-cgi/trace` 由 Cloudflare 自己应答，用哪个站点名问都一样。
  `workers.dev` / `pages.dev` 的名字在部分网络里一出现在握手里就被掐断（实际连接靠 ECH 藏名字，探测不走 ECH），
  这两类直接用 `speed.cloudflare.com`；自定义域名先用自己，握手或应答不对再换它试一次。
- **测下载**：经被测地址从 `speed.cloudflare.com/__down` 下载，最多 6 秒，报峰值（最好的连续 1 秒）和平均值，测的过程中实时更新。
  一次只测一个（并发会互相抢带宽）；可以单测一行，也可以批量测延迟最低的 8 个。
  端点对单次下载大小有上限（实测 1 亿字节返回 403，5000 万可以），从 5000 万、2000 万、1000 万依次试。
- SOCKS5 / HTTP 全局出口不是 Cloudflare 的地址，仍经代理内核测。通用订阅（非 edgetunnel）保持原来的测法。
- 导入放宽：IP、`IP:端口`、域名、`#备注`、空白或逗号分隔、测速工具导出的 CSV 都认，不是地址的列自动丢掉；
  也可以贴一个列表网址（`https://…/ip.txt`），导入时拉取一次。网段（CIDR）不支持。一次最多 500 个地址。
- 限制：直接探测量的是"本机到这个地址"，本机如果开着别的全局代理，量到的是那个代理。延迟和速度都在本机测，换个网络结果会变。

面板随之重排（`companion/ext/popup.*`）：

- 主界面只有四块：实例头、当前两路出口、伪装设备 / 时区 / 语言一行（点开是指纹设置）、线路三行（地区 / 入口 / 反代）。
- 点任一行进入占满面板的列表：国旗筛选、优选 / 反代筛选、按延迟或下载排序、每行可单独测下载。
- 文字尽量换成图标，完整说明放在悬停提示里。国旗以实测为准；还没测到时按备注里的国家猜一个，显示得淡一些。
- 打开面板时，上次探测超过 10 分钟就自动重测一遍。

### P-8 出口 / 入口各自的自动与手动、线路、IP 类型与纯净度（2026-11-13，面板第五版）

**两个开关。** 出口和入口各有一个"自动"开关（`exitMode` / `entryMode`，空 = 自动）。只有这两个字段改模式；
在列表里点一行由面板显式带上 `manual`，选国家带上 `exitMode: auto`。旧的 `auto` 字段只为兼容保留。

- 出口自动：只认国家。当前反代还通、还在这个国家就不动；否则按"用户自己加的在前、没被别的实例占用的在前、延迟低的在前"换一个。
  这个国家没有反代时，退回去找出口在这个国家的入口。**绝不悄悄换国家**：找不到就给 `noexit:<国家>` 提示，线路保持原样。
  没选国家：用最快的入口，反代配成和入口同国。
- 出口手动：钉死，不换。Cloudflare 那一路不通时只提示。
- 入口自动：反代那台机器自己能当入口就用它；不行就用延迟最低的，同国优先，没有再全局。
- 入口手动：钉死。
- 通用订阅（非 edgetunnel）节点就是出口，只有一个开关。
- "换一个"（`POST /api/instances/{id}/next`）：在当前国家里按上面的顺序轮着换，到头回到第一个。出口手动时拒绝。

**自动换线**（`refreshTry`，最多两次）：整条线不通 → 换入口（仅入口自动）；普通网站通、Cloudflare 网站不通 → 换同国的下一个反代（仅出口自动）。
换成功后给 `switched` 提示，面板上说一句"已自动换线路"。

**线路（profile）。** 一个 edgetunnel 订阅地址里可以有几个 Host、几种传输（ws / xhttp）。每个 Host + 传输是一条线路，实例记自己用哪一条（`proxy.profile`）。
同一后缀下超过四个 Host 的（泛域名）并成一条 `*.后缀`，里面的 Host 按实例平分。新实例只在和第一条线路同传输的线路里分配，所以 xhttp 要手动选。
测速和直接探测用第一条线路。同一地址同一 Host 的 ws 和 xhttp 是两个节点（节点 key 里带传输，ws 不带，旧 key 不变）。
xhttp 只验证到 `mihomo -t` 认配置，**没有实连过**。

**IP 类型与纯净度。** 来源 `ip.net.coffee` 的 `trust_score`（0–100，越高越干净）和住宅 / 机房 / 移动标记；查不到类型时用 ip-api 的 `hosting` / `mobile` 补。
按 IP 缓存 7 天（`state/ipq.json`），失败的 10 分钟后重试，6 路并发，一轮最多 400 个。有健康的实例时经它的探测端口去查，否则直连。
查不到就不显示，不编数字；保留地址返回的 0 分丢掉。这会把出口 IP 发给第三方，设置里可以关（`ipqOff`），关掉后以前查到的也不显示。

**面板。** 宽 320 px，样式全部内联在 `popup.html`。订阅一栏：线路条数、当前线路（点开切换）、加号再加一个订阅地址（名字留空时用地址的域名）。
出口 / 入口各一张小卡：名称 + 自动开关，下面是当前值；手动时点进占满面板的列表（两行一条：地址 + 延迟，类型 + 纯净度）。

### P-3 时区

- 默认跟随出口：启动前先探测两路出口（`https://www.cloudflare.com/cdn-cgi/trace` 和 `https://checkip.amazonaws.com`），按国家取时区和语言，
  作为 `--timezone`、`--lang` 传给内核。两路都探测失败且时区是“自动”时拒绝启动，并提示可以改成固定时区后强行启动。（**2026-11-17 改，见 F-HEAL**：不再拒绝启动，窗口照开、停在断流。）
- 运行中出口时区变了：切断，并在界面提示需要重启该实例。
- 实测：页面与 Worker 里的时区、`Intl`、时间偏移都跟着变。

## 组件下载与安装

### D-1 下载途径

- 两个组件（浏览器内核约 190 MB、mihomo 约 22 MB）都在 GitHub 上，国内直连经常超时。旧代码只有一条直连、整体 10 分钟超时、不能续传。
- 现在依次尝试：直连 → 本机已有的代理（环境变量、Windows 系统代理、常见端口 7890 / 7897 / 10809 / 10808 等，先探测确实是代理）→ GitHub 镜像
  （设置里的镜像前缀优先，其后是内置的几个）。订阅拉取用同一套途径，但不走镜像。
- 断点续传（`.part` 文件，换途径接着下）；25 秒没有数据算卡住；第一轮里平均不到 30 KB/s 的途径会被放弃，第二轮不再嫌慢；
  返回网页的途径直接跳过。
- 镜像不可信，所以**下载完一律校验内置的 SHA-256**（取自上游发布页的 digest），不符就丢弃换下一个途径。换固定版本时要同时改 `internal/kernel/fetch.go` 里的校验值。
- 需要下载浏览器内核时，用系统默认浏览器打开本机的进度页 `http://127.0.0.1:<端口>/setup#<令牌>`（令牌在 `#` 后，不会发给任何服务器）。
  页面显示进度、速度、当前途径、失败原因、重试，以及手动安装的位置。
- 代理内核出问题（下载失败、被安全软件拦截）不再挡住浏览器：普通窗口照常能开，面板上显示原因和重试。

### D-2 安装程序

- NSIS 脚本 `installer/masktab.nsi`，一份脚本出两个包：普通包（只有 `masktab.exe`）和完整包（加浏览器内核与 mihomo）。
- 装到 `%LOCALAPPDATA%\Programs\MaskTab`，不要管理员权限。数据目录仍是程序目录下的 `data`（与解压版一致，所以解压版用户选原目录安装即可接上）。
- “只更新变了的部分”的规则：`masktab.exe` 总是替换；`mihomo.exe` 靠 `mihomo-<版本>.ver` 标记，版本相同跳过；
  内核目录 `kernel\fingerprint-chromium\<版本>\installed.ok` 存在（或 `data\kernel` 里已有这个版本）就跳过，版本变了才装并删除旧版本；`data` 从不碰。
- 升级前调用 `masktab.exe -quit` 让运行中的 MaskTab 自己关窗口退出，等文件解除占用；20 次不成再强制结束。
- 核心服务找组件的顺序没变：程序目录 → `data\core`、`data\kernel` → 设置里的内核路径 → `程序目录\kernel`。所以安装程序只要不动 `data`，以前下载的也继续用。
- CI 在 Windows 机器上构建两个包，把完整包静默安装后**对装好的那一份跑冒烟测试**，再验证：运行中升级、完整包覆盖安装跳过内核、卸载保留数据。
  两个包发布到 Releases。

### D-3 两端同步发布（2026-11-14，需求方：“合并吧，之后一起更新同步发布”）

- 安卓分支 `demo/android` 并入 `main`，以后两端都在 `main` 上改，不再分开。
- 一次推送到 `main` = 一个版本号 `0.1.<CI 运行序号>` = 一个 Release，里面同时有 `MaskTab-Setup-Full.exe`、`MaskTab-Setup.exe`、`MaskTab-android-arm64-v8a.apk`。
- 做法：`ci.yml` 在 `main` 上调用 `android.yml`（`workflow_call`），再由单独的 `release` 任务等单元测试、Windows、Linux 冒烟、安卓构建与模拟器冒烟**全部通过**后一起发布；任何一项不过就整个不发，不会出现只发了一端的版本。
- 安卓版本号（`versionCode` / `versionName`）取 `GITHUB_RUN_NUMBER`；被 `ci.yml` 调用时就是 CI 的运行序号，所以和电脑版一致，并且比之前的试用版（`android-v0.1.9 / 13 / 14`，按安卓工作流自己的序号）大，可以覆盖安装。
- 代价：只改电脑端的代码也要等安卓模拟器测完（约 15 分钟）才发版；Release 多 128 MB 的 APK。
- 其它分支：`ci.yml` 照常跑电脑端测试、不发版；`android.yml` 在安卓相关文件有变化时自己跑、只出产物。
- 之前的三个安卓试用版（prerelease）保留，不再新增。

## 核心服务

### C-1 本地接口的访问控制

- 只监听 `127.0.0.1` 的随机端口；必须带 `X-MaskTab-Token`；`Host` 必须是 `127.0.0.1`；如果带 `Origin`，必须是伴随扩展的来源。
- 端口和令牌写在 `data/state/running.lock`，每个实例的伴随扩展副本里有一份 `config.json`。
- 实测：无令牌 401，外部来源 403，错误的 Host 403。

### C-2 崩溃恢复

- 核心服务把各实例内核的进程号写在 `state/runtime.json`，mihomo 的写在 `core/mihomo.pid`。
- 启动时如果发现上次遗留的进程还在（并且确认是自己的内核 / mihomo），先结束它们，再按恢复列表重新启动上次开着的实例；
  内核带 `--restore-last-session`，标签页会回来。
- 为什么必须清理：遗留的内核进程会让新启动的内核把窗口交给旧进程后立刻退出；遗留的 mihomo 会占着端口。

### C-3 入口行为

- 第二次运行 `masktab` 时发现已有核心服务，就请求它打开普通窗口（`POST /api/open`）后退出。
- 没有托盘图标（未做）。全部窗口关闭 6 秒后核心服务自动退出，除非带 `--keep` 或 `--no-open`。
- #0 是普通窗口，不开指纹，代理默认关闭。实例编号~~只增不复用~~ **2026-11-17 改，见 F-HEAL**：新实例用最小的空号，编号可以手动改、可以一键整理。

### C-4 删除实例

- 主进程退出后子进程还会再写几个文件，Windows 上文件可能仍被占用，所以删除资料目录要循环删到确实不存在为止（最多约 5 秒）。
- 停止、重启、删除这几个接口都是立即返回、后台执行；调用方要看 `/api/state` 里的 `rt.running` 才知道做完没有。

## 测试办法

- 没有显示器时用无头模式，见 `AGENTS.md`。内存 2 GB 的机器上同时最多开一两个无头实例，否则调试端口会没有响应。
- 假节点服务端：再起一个 mihomo，配置里放 ss 入站（两个端口、不同密码）和 vless+ws+TLS 入站（自签证书，订阅链接里带 `allowInsecure=1`），
  订阅文件用 `python3 -m http.server` 提供。mihomo 不接受没有证书的 vless 入站。
- 假 edgetunnel：`go run ./scripts/fakeet -port 8443 -colo NRT -loc JP [-lag 30] [-listen ::]`，一个端口一个进程（自签证书，订阅链接带 `allowInsecure=1`，server 写 `127.0.0.1`）。
  它回 `/cdn-cgi/trace`（直接探测靠这个），转发 VLESS over WebSocket，目标是 Cloudflare 的地址时改连路径里的 `proxyip`，所以两路出口和真的一样。
  杀掉某个端口的进程 = 这个入口坏了；入口地址派生出来的"反代"是假的，选中它 = 反代坏了。自动换线就是这么测的。
- 面板截图：用调试端口新开 `chrome-extension://<ID>/popup.html`，`Emulation.setDeviceMetricsOverride` 设成 320 宽再截。
- 调试扩展后台：用调试端口附着到 `service_worker` 目标求值。不要从扩展页面 `import('./background.js')`，那会启动长轮询、永远不返回。
- `pkill -f "模式"` 可能把调用它的 shell 也杀掉，模式里用 `[x]` 写法，例如 `pkill -f "[h]ttp.server 28080"`。

### N-1 出站绑定物理网卡，绕过本机 TUN（2026-11-14）

- 问题：浏览器只走本地 mihomo，但 mihomo 的出站按系统路由表走；本机开 TUN 后会被二次代理，出口 IP、延迟、DNS 都变。
- 做法：自动识别物理网卡（排除虚拟网卡名、无 MAC、TUN 地址段 198.18.0.0/15 等），mihomo 全局 `interface-name` 绑定；
  绑定时 DNS 模块打开，用 223.5.5.5 / 119.29.29.29 / DoH（按 IP），不用 `system`（TUN 的 fake-ip 会把系统 DNS 劫持成 198.18.x）。
  核心服务自己的直连请求用 `netx.BindDialer`（Windows IP_UNICAST_IF、Linux SO_BINDTODEVICE、macOS IP_BOUND_IF）。
- 设置 `bindIface`：空 = 自动（默认）；`off` = 不绑定；其它 = 指定网卡名。识别失败时不绑定（行为与以前一样）并写日志。
- 风险：识别错网卡会导致全部不通（R-1 下是切断，不会泄漏）；遇到时在设置里关掉或指定网卡名。没在 Windows + TUN 上实测。
- 回退：设置里选“关”，或删掉 `Input.Interface` 的赋值。

### N-2 IPv6 的入口地址能用；域名解析查全（2026-11-16，需求方：“优选 IP 好像不能用……最后节点显示解析失败”）

复现（沙箱）：假 edgetunnel 监听 `[::1]:8444`，把它加进地址库。直接探测通（1 ms），实例用它当入口就报“域名解析失败”；
代理内核的日志是 `[::1]:8444 connect error: dns resolve failed: ip version error`。

**原因 1：内核的 IPv6 是关着的。** `configgen.go` 顶层和 `dns` 里都写着 `ipv6: false`。mihomo 在这个设置下不连任何 IPv6 的服务器地址，
报的错里带 `dns` 字样，`friendlyErr` 就翻成了“域名解析失败”。只有 AAAA 记录的域名展开后全是 IPv6，所以整条都不能用。

- 改成 `ipv6: true`（两处）。
- 这一项只管“内核自己去连谁、怎么解析”。网页的流量不受它影响：每个实例的监听口用 `proxy:` 直接绑在自己的策略组上，不过规则
  （规则只有兜底的 `MATCH,REJECT`），目标地址原样交给节点，由服务端去解析、去连。所以打开它不改变网站看到的出口。
  对照实测（2026-11-16，沙箱，同一个假节点，v0.1.67 的核心 `ipv6: false` 和这一版 `ipv6: true` 各跑一遍，经实例访问）：
  `http://[::1]:28081/x.txt` 两版都是 200，节点端日志都是 `::1:28081`；`https://[2606:4700:4700::1111]/` 两版节点端日志都是 `2606:4700:4700::1111:443`。
- 本机没有 IPv6 的网络上，IPv6 地址仍然连不上。这时写“本机网络没有 IPv6”（`cfprobe.NoIPv6`），不再写“网络不可达”或“解析失败”；自动选线本来就不选不通的地址。

**原因 2：域名解析不全（`ResolveExit`）。** 三处：

1. 只要有一个 IPv4 就把 IPv6 全丢掉。
2. 只查 A / AAAA，不查 TXT。edgetunnel 解析反代域名的次序是 TXT → A → AAAA（`_worker.js` 的“解析地址端口”），TXT 里是逗号分隔的 `IP:端口`；用 TXT 的域名我们一个都看不到。
3. 用的是系统解析：本机开着 TUN 时拿到的是 198.18.x.x 的假地址；安卓上（没有 `/etc/resolv.conf`）查不了 TXT。

改法：新包 `internal/dnsx`。

- TXT、A、AAAA 都查；问系统 DNS、223.5.5.5、119.29.29.29，结果取并集去重（TXT 在前，然后 IPv4、IPv6），最多 64 个。公共 DNS 的请求走 `netx.BindDialer`。
- 丢掉 0.0.0.0、组播、198.18.0.0/15。
- TXT 里没写端口的按 443（和服务端一致）；域名里的 `.tp端口` 约定也认（`proxyip.tp8443.example.com`）。
- 每种记录都有 DNS 答复之后最多再等 1.5 秒：实测 119.29.29.29 对 50 个 A 记录的大答复一直不回，不能让它拖满 8 秒。
- 失败时保留上一次的结果，原因记在 `ExitEntry.ResolveError`，地址库那一行用红字写出来；“立即解析”的提示写解析出几个或失败原因。
- `Resolved` 的每一项是 IP 或 `IP:端口`（TXT 自带端口的）。实例里记的 `exitIp` 就是这一项，旧数据（纯 IP）不用迁移。
- 地址变了就重新探测一遍（以前定时解析出新 IP 后没有延迟、不会被自动选中）。启动 5 秒后先解析一遍（设成“不刷新”的不动），升级后不用等 3 小时。

**原因 3：IPv6 加端口拼错。** `exitValue` 用 `ip + ":" + 端口`，IPv6 会拼成 `::1:8443`，是另一个合法的 IPv6 地址，入口和反代都跟着错。

- `exitValue` / `pipAddr` 统一输出 `IPv4`、`IPv4:端口`、`[IPv6]`、`[IPv6]:端口`。用户原样粘贴的不带方括号的 IPv6 也在这里规整（不改存储的值）。
  新旧版本的 edgetunnel 都认带方括号的写法（旧版对不带方括号的 IPv6 会把最后一段当端口）。
- 入口地址给内核时不带方括号（`nodeRef.Server`），由 `hostPort` 拼键时再加。

**界面**：IPv6 最长 39 个字符，列表里原来用“…”截掉。新增 `ui.js` 的 `ipSpan` / `isV6` 和样式 `.ip6`：小一号字、在冒号后面允许折行，不截断（UI-9 的“IP 不截断”）。
入口列表、出口列表、节点页“正在用的”两行、地址库都用它。IPv6 带端口时界面上也写成 `[IPv6]:端口`。

检查：

- `go test`：`dnsx`（假 DNS：两种地址族都留、只有 AAAA、TXT 在前并带端口、多个 DNS 取并集、丢假地址、失败原因、`.tp`）、`core/ipv6_test.go`（`exitValue` 16 种写法、
  入口 / 反代列表、选中后的取值、日志翻译）、`configgen`（三种模式都开着 ipv6）、`cfprobe`（IPv6 不可达的说法，含 Windows 的报错文字）。
- `preview-pages.mjs` 加 8 项（412 / 320 宽 × 地址库、节点页、入口列表、出口列表：IPv6 写全、不出屏幕、失败原因写出来）。
- 联调办法：`go run ./scripts/fakeet -listen :: -port 8443`（新增 `-listen`），`/etc/hosts` 里加 `::1 v6only.test`、`127.0.0.1 dual.test`、`::1 dual.test`，
  地址库导入 `[::1]:8444`、`v6only.test:8443`、`dual.test:8444`。

没有验证：公网 IPv6（沙箱没有）；Windows 上绑定网卡时的 IPv6（`IPV6_UNICAST_IF`，代码早就有，没跑过）；手机。
没有做：自动判断本机有没有 IPv6 并在页面顶上提示一次（现在是每个 IPv6 地址各写一句）；SOCKS5 / HTTP 出口的 IPv6 写法没有动。

### M-3 标记网站：录入登录（2026-11-14，需求方：“先把功能跑通，之后优化”）

- 是什么：自动识别认不出的登录页，或者想明确记下来的网站，用户点“录入”后照常登录一次，程序记下两样东西：
  - **规则**（全部实例共用）：这个网站哪个框填邮箱 / 账号 / 手机号、哪个框填密码。只有选择器，没有账号内容。
  - **账号**（只属于当前实例）：这次输入的用户名和密码，进密码库。
- 入口两个：聚焦像登录框的输入框时旁边出现“录入”小按钮（只在这个网站没有规则、本实例也没有它的账号时出现）；实例菜单里的“录入登录”（任何时候都能点，用来重录）。
- 结束条件 = 登录成功，判断方法：点过登录之后登录框不见了。
  - 录到了密码：密码框不见超过 1.2 秒就算成功（后面的两步验证页不用等）。
  - 只录到账号（短信登录、两步登录的第一步）：账号框也不见、点登录超过 6 秒、页面加载超过 3 秒才算，免得把“第一步 → 第二步”的切换当成成功。
  - 点了登录 12 秒登录框还在：当作没登上，接着录；用户重输就覆盖。
  - 录入条上有“完成”（立刻保存已录到的）和“✕”（取消；这个标签页这个网站 10 分钟内不再自动录入）。10 分钟没完成自动放弃。
- 认框：只认用户亲手输入的（`isTrusted`），点登录那一刻再把粘贴 / 自动填好的读一遍。类型按内容猜：含 `@` 是邮箱，6–15 位数字且像手机号是手机号，其余是账号；验证码框（名字像 code / otp / 验证码，或很短的纯数字框）不记；密码提交之后才出现的新框不当成账号。
- 选择器：稳定的 `id` → `name` → 密码框类型 → `autocomplete` → `placeholder` → 输入框类型；带长数字 / 哈希的 `id`、`name` 视为不稳定，跳过。同一选择器命中多个时记下第几个。
- 共用规则怎么生效：别的实例打开有规则的网站——本实例有这个网站的账号，按规则找框填；没有，自动进入录入，登录一次就记住（自动录入不改写规则，只有手动录入才写）。
- 跨页面的登录流程：录到一半的内容（含密码）暂存在扩展后台的内存里，按“标签页 + 主域名”，10 分钟，换页后接着录；不落盘，不进网页能读到的存储。
- 存储：规则放在密码库文件里（`rules`），接口 `PUT /api/vault/rule`、`DELETE /api/vault/rule?site=`，`GET /api/vault/match` 的回复里带 `rule`；状态里 `vault.rules` 只有站点、类型、由谁录入，不带选择器。桌面（Go）和安卓（Kotlin）各一份，形状相同。
- 从菜单触发：桌面由弹出面板直接给当前标签页发消息；安卓由后台转给这个实例正显示着的网页（内容脚本在页面显示 / 隐藏时报一声），转不到就记下来，2 分钟内下一个显示出来的网页接手。
- 录入条默认在页面顶部中间，会挡住输入框 / 按钮时挪到底部；条本身不拦点击。
- 测试：`scripts/rec-test.mjs`（Playwright，Chromium 和 Firefox 各跑一遍，后台用假的顶替）；Go 接口测试 `TestRuleRoutes`、`TestRules`。
- 已知不足（之后优化）：登录按钮在内嵌框架里的网站不支持（内容脚本只在顶层页面工作）；用 CSS 把普通文本框伪装成密码框的网站，密码会被当成账号；规则目前只用来找框，`path`（哪一页）记了没用上；“怎么用？”的说明在手机上是悬停提示，看不到。


### M-4 录入登录闭环：存到哪、谁来存、提示与站点图标（2026-11-13）

需求方反馈（电脑版 0.1.43）：录入能走完，但再打开登录页不自动填，账号管理里也没有这个网站；密码像是内核自带的密码管理填的。

- **查到的原因**（用 0.1.43 的逻辑在仿真网站上复现）：保存是在网页里、登录成功之后才发的，用的是“当时所在页面”的地址。
  - 登录页在 `login.x.com`、登录后跳到 `www.x.com`：账号和规则都记在了 `www.x.com` 名下，登录页自己名下什么都没有。
  - 登录页在另一个站（单点登录）：跳走时页面已经没了，什么都没存下。
- **谁来存**：改成后台存。网页只发一条消息（`vault:remember` 或 `vault:rec-finish`），后台一次办完“存账号 + 存规则 + 清暂存”，
  所以提交后立刻跳转也丢不了。录入中的内容按标签页暂存（10 分钟，不落盘）。录入已提交且有密码时关掉标签页（登录弹窗）也照样保存。
- **存到哪**：每个输入框由后台盖上“发送方的真实地址”，账号和规则都记在**输入框所在的网站**名下，不是登录后落脚的网站。
- **匹配**：`www.` 和裸域名算同一个站。同一实例里兄弟子域名的账号（按简化的主域名算；`github.io` 这类公共后缀不算；协议要相同）
  只进选择列表、带上来源主机名，**不自动填**（M-1 的“站点完全匹配才自动填”不变）。
- **登录页提示**：页面像登录页、这个网站没有规则、本实例也没有它的账号时，右上角出一张小卡片“录入这个网站的登录？”，点“录入”直接开始；
  点“不用”30 天内这个网站不再问（按实例 + 主机名记在扩展本地存储里），菜单里的“录入登录”仍然可用。原来输入框旁边的小按钮保留。
- **站点图标**：记住账号后，内容脚本顺手取一次网页图标（不带登录状态，只收图片，不超过 48 KB）交给核心服务，和密码库存在一起；
  只为“密码库里有账号的主机名”存。界面只读本机接口 `GET /api/vault/icons`，不向外发请求。显示顺序：内置品牌图标 → 存下的网页图标 → 字母块。
- **内核自带的密码管理**：偏好文件里本来就关了（F-PWD）；这次伴随扩展再用 `chrome.privacy` 关一次（扩展设的值压过设置页）。
  已经存在内核自己密码库里的旧记录不删（那是用户的数据），需要用户自己在 `chrome://password-manager` 里清。
- **代码位置**：后台逻辑两端共用 `companion/ext/vaultmsg.js`（`MTVault(env)`），两端后台只提供 `env`：怎么发请求、标签页属于哪个实例、暂存放哪
  （电脑 `chrome.storage.session`，手机内存）。
- **测试**：`scripts/rec-test.mjs`（真 `autofill.js` + 真 `vaultmsg.js` + 真核心服务，网站是仿真的，Chromium / Firefox 各 38 项）；
  `scripts/ext-e2e.mjs`（把伴随扩展真的装进 Chromium 走一遍，16 项）。两个都进了 CI。

### D-4 两端同一个核心服务、同一份面板代码（2026-11-14，需求方：“把电脑端和手机端功能尽可能统一一致，之后修改任何一个功能双端都会同步修改”）

**以前**：手机端的实例、订阅、选线、密码库是用 Kotlin 另写的一套（`Store.kt` `Mihomo.kt` `Vault.kt` `Identity.kt`），界面也另画（`android/ext/main.js` 里的节点页、订阅页、设置页）。
电脑上有的功能（edgetunnel 识别、出口 ProxyIP / 入口优选 IP、自动选线、多订阅、地址库、测速、纯净度…）手机上都没有，改一个功能要改两遍。

**现在**：
1. **核心服务只有一份**。APK 里带着电脑版那个程序（`cmd/masktab`，编成 `jniLibs/<abi>/libmasktab.so`），app 把它当子进程启动：`-host android`（“宿主模式”）。
   宿主模式下它只少做一件事——不启动浏览器进程（浏览器是 GeckoView，由 app 管）；实例、订阅、选线、mihomo 配置、出口探测、时区语言、密码库、录入规则全是电脑版的原代码。
   Kotlin 那四个文件删了。`Bridge.kt` 变成转发：页面的请求原样转给核心服务（同样的路径、参数、返回值）。
2. **界面共用到文件**。节点面板 = `companion/ext/panel.js` + `panel.css`（电脑放进工具栏弹窗，手机放进“节点与出口”页）；
   订阅与出口、设置 = `pages.js`；实例菜单、实例管理、自动填写本来就是共用的。安卓构建时把这些文件拷进 APK，仓库里只有一份。
3. **差别用“内核能力”表达，不写两份**。核心服务在状态里报 `kernel.caps`（`platform` 能否换系统 / 浏览器、`spoof` 能否逐项开关伪装、`extLib` 有没有扩展库、`live` 改指纹是否免重启）和 `host`；
   共用的页面按这个决定显示哪几项。手机上没有的只有内核做不到的那几样（见 docs/android.md“两端还剩的差别”）。
4. **一起验证**。CI 里同一份核心服务状态分别画电脑版弹窗和手机页面，面板文字必须一样（`preview-pages.mjs`）；`go test` 两端共用；模拟器冒烟测试里核心服务真的在安卓上跑。

**宿主模式的规矩**（`internal/core/host.go`）：
- 实例没有“打不开”：浏览器一直在，没有可用出口时实例照样算运行着，只是断流（mihomo 里是 REJECT），原因显示在面板上；选好节点后自己恢复。**任何情况下不回落直连。**
- 实例端口固定为 21000 + 编号（被占用才换），内置扩展按它分流。
- 改时区 / 语言 / 指纹不用重启（`caps.live`）：页面内的伪装脚本每次加载网页时向 app 要最新的参数。
- 密码库的密钥由 app 从 Android Keystore 解出来，经环境变量 `MASKTAB_VAULT_KEY` 交给核心服务；库文件离开这台手机解不开。
- app 退出（标准输入关闭）核心服务跟着退出，连同 mihomo。
- 旧数据（0.1.41 及以前的 `files/state.json`、`vault.bin`）第一次启动时搬进核心服务（`POST /api/host/import`）：实例 id、编号、名称、颜色、指纹种子、固定的时区语言、账号密码、录入规则原样保留；
  订阅重新拉一次，原来钉着的节点按名字对上，对不上的保持断流；订阅当时拉不下来也不改成直连。旧文件改名 `.old` 留底。

**代价**：APK 每个架构大约多 10 MB（Go 程序）；手机上多一个常驻子进程。
**放弃的做法**：把电脑版的逻辑用 Kotlin 再写一遍（两份代码永远对不齐）；把内核换成 xray（见上一轮的答复）。

## 安卓版（2026-11-14，起初在分支 demo/android，已并入 main，见 D-3；详见 docs/android.md）

### A-1 安卓用 GeckoView，不用计划第 9 章的系统 WebView（偏离计划 D14）

- **结论**：安卓版内核用 Mozilla 的 GeckoView（固定 160.0.20261104181552），需求方 2026-11-14 拍板。
- **原因**：
  - 计划里的系统 WebView 方案本身就把“Google 登录可能被拦”（VA2）列为风险，备选正是 GeckoView。
  - 多实例隔离：GeckoView 有 `contextId` 容器，一个进程里多个实例同时存活、各自 Cookie / 存储隔离；WebView 要靠“进程槽位 + `setDataDirectorySuffix`”，每个实例一个进程、数量有上限、切换要重启进程（VA1 未验证）。
  - 每实例代理：WebView 的 `ProxyController` 是整个进程一个代理；GeckoView 里内置扩展的 `proxy.onRequest` 可以按标签页分流，一个进程里多个实例走不同出口。
  - 扩展：GeckoView 支持 WebExtension，桌面伴随扩展的 `autofill.js`、`menu.js`、`instances.js` 能复用；用户还能从 AMO 装扩展（计划里手机端原本“不做扩展”）。
  - 内核版本由 app 自带、跟着 Firefox 正式版走，不受手机系统 WebView 版本影响。
- **代价**：APK 大（每个架构约 80 MB 的 libxul）；网站看到的是安卓火狐（不伪装 Chrome）；只能装 AMO 签名的火狐扩展；页面指纹在扩展层做，弱于桌面内核级；Service Worker 第一版关闭（A-3）。
- **回退**：WebView 方案仍可按计划第 9 章做，`android/` 下的 mihomo、密码库、扩展页面大部分可复用，只有 `Core.kt`（会话、容器、代理分流）要重写。

### A-2 mihomo 的 proxy-providers 必须写 `proxy: DIRECT`

- 沙箱实测（mihomo v1.19.34 Linux arm64）：provider 不写 `proxy` 时，拉订阅这个请求也走规则匹配，被兜底的 `MATCH,REJECT` 拒掉，日志是 `EOF`。写 `proxy: DIRECT` 后正常拉取。
- 订阅里的节点不在 `/proxies/<名>` 下，单测延迟要用 `/providers/proxies/sub/<名>/healthcheck`。

### A-3 关闭 Service Worker

- Service Worker 发出的请求 `tabId = -1`，而 GeckoView 里 `details.cookieStoreId` 不准（bug 1948114），分不出属于哪个实例。为了守住“认不出就拒绝、绝不直连”，第一版用偏好 `dom.serviceWorkers.enabled: false` 关掉。
- 影响：离线、推送等依赖 Service Worker 的网站功能没有。以后 GeckoView 修好 cookieStoreId 后可以打开，改 `Core.writeGeckoConfig` 与 `ext/background.js` 的 `proxy.onRequest`。

### A-4 标签页 → 实例的识别

- CI 模拟器里看到：GeckoView 容器标签页的 cookieStoreId 就是 `firefox-container-` + contextId，例如 `firefox-container-mt-a14fd374`。
  所以后台直接从 cookieStoreId 认实例（`tabs.get(tabId).cookieStoreId`，不用 `details.cookieStoreId`，见 bug 1948114）。
- 兜底：app 开的每个标签先进扩展自己的引导页 `newtab.html#inst=<id>&go=<网址>` 登记，再跳网址（扩展页不走代理，第一跳不漏）；
  网页内容脚本的原生消息由会话自己的 MessageDelegate 接收（app 按会话知道实例），再告诉后台。网页伪造不了这两条。
- ~~指纹脚本按容器 `contentScripts.register({cookieStoreId})` 同步注入。~~ **这条是错的，已废弃，见 A-7**：调用被接受不等于按容器生效。
- GeckoView 的坑：会话里打开的扩展页面（以及内容脚本）发的原生消息只交给**这个会话**的 MessageDelegate，没设就一直挂着不回；回复不能是 JSONObject（报 “Invalid event data for callback”），一律回 JSON 字符串。

### A-6 安卓内置页面：耗时操作全部后台化，页面永远有内容（2026-11-14）

- **起因**：用户真机（安卓 15+，edgetunnel 订阅）反馈点“节点与出口”“指纹与时区”后白屏、无响应或一直转圈。
- **查到并修掉的问题**：
  1. `fp.js` 在真 Gecko 里把画布、音频、`Intl…resolvedOptions()` 改坏了：内容脚本里包出来的函数读页面传来的 `arguments` 会被拒绝（`Permission denied to access property "length"`），用到这些接口的网站直接白屏。以前只在 Chromium 普通页面里测过，测不出来。现在用 `exportFunction` + 显式参数重写，并加了自检页 `fpcheck.html`。
  2. `PUT /api/sub`、`POST /api/nodes/test` 同步等 mihomo 拉订阅 / 测完所有节点，节点多、多数不通时要几十秒，期间页面没有任何反馈。
  3. 节点页在渲染过程中发起 `GET /api/nodes`，失败时又触发重画，形成循环。
  4. 页面脚本出错或接口不回时没有任何兜底，表现就是白屏。
- **做法**：见 `docs/android.md`“界面”一节。节点“自动”改成有粘性：当前节点还通就不换，避免每次测速都换出口 IP。
- **没有确认的**：模拟器里旧版从菜单点进这两页是能打开的（没有复现用户的白屏），所以无法证明上面几条就是用户手机上的全部原因；真机 edgetunnel 订阅对 `clash.meta` UA 返回什么也没验证。为此加了“诊断信息”。
- **顺带**：固定调试签名，后续版本可以覆盖安装。

### A-7 指纹参数改为“消息 + 同步请求”交给内容脚本，废弃按容器注册（2026-11-14）

- **问题（第一版就有，第二版的 CI 自检页抓到）**：`contentScripts.register({cookieStoreId: "firefox-container-mt-<id>"})` 在 GeckoView 里不分实例。
  安卓上 Gecko 把 cookieStoreId 的后缀当数字解析（`ext-toolkit.js` 里 `parseInt`，注释写着 Bug 1643740），`mt-<id>` 得到 NaN，匹配条件退化成“默认容器”；
  而 GeckoView 的会话隔离用的是另一个属性（`geckoViewSessionContextId`），所有标签页的 userContextId 都是 0——于是每份注册的脚本对**所有**标签页生效，谁注册得早谁赢。
  后果：所有实例的网页用的是同一个实例的种子、时区和语言（Cookie 和代理分流不受影响，那两样不靠这个）。
  CI 里的表现：实例 #3（东京）的自检页有一次拿到的是实例 #2 的参数（时区 UTC、语言 en-US）。
- **做法**：`fp-boot.js` 在 `document_start` 发消息 `{t:'fp:who', n}`（消息自带来源标签页，后台按标签页认实例，和代理分流用的是同一张表），
  紧接着发同步请求 `https://fp.masktab.invalid/<扩展内部编号>/<n>`；后台 `webRequest.onBeforeRequest` 把两者对上，跳转到 `fpcfg.json?c=<参数>`，内容脚本读跳转后的地址。
  请求不出网（域名不存在，且在发出前就被跳转）。网页不知道扩展内部编号，自己发这个请求只会被取消。
- **为什么不只用请求**：内容脚本发的请求在 webRequest 里 `tabId` 是 -1，认不出标签页（沙箱桌面火狐实测）。
- **代价**：每个页面 / 框架多一次同步往返（桌面实测 10–40 毫秒）；消息 400 毫秒没到就放弃，退回异步。
- **证据**：沙箱真火狐 160 + 整个内置扩展，两个实例交替开自检页各拿各的参数；CI 模拟器结果见 PROGRESS。真机没验证。

### A-5 安卓版的构建方式

- AGP 9.5.1（自带 Kotlin 编译），根项目声明 Kotlin 插件 2.4.21 是为了能读 GeckoView 160 依赖的 kotlin-stdlib 2.4；compileSdk 37.2 是 GeckoView 的 AAR 元数据要求的。

### A-8 内置页面不再开对话框：一个 GeckoView、一个常驻页面会话，换路由显示（2026-11-14，第三版）

- **问题**：第二版（0.1.9）发给用户后，真机上点头像能出菜单，但从菜单点“账号与密码 / 节点与出口 / 指纹与时区 / 新建实例 / 导入邮箱 / 管理实例”任何一项都白屏或闪退，还经常卡死。
  CI 模拟器里同样的真点击全过——**模拟器通过不能说明真机没问题**（第二版犯的就是这个错）。
- **真机上的原因没有确认**（拿不到手机日志）。能确定的只有：出问题的每一项都走同一条路——关掉菜单的对话框和它的 GeckoView / 会话，再新建一个对话框 + GeckoView + 会话；
  “新建实例”还是在那个会话自己的消息回调里把它关掉的。也就是每点一下都在销毁、重建绘制表面和内核会话。
- **做法**：不修补这条路，直接去掉它。全应用只有主界面那一个 GeckoView；内置页面用一个常驻会话，显示 / 收起就是 `setSession` 换进换出（与切换标签页相同）；
  页面之间只改路由。于是从菜单点任何一项不再经过任何原生窗口操作，只是同一个页面里换一下 `#`。
- **同时补上取证手段**：原生诊断窗口（见 `docs/android.md`），白屏、卡在启动页时也打得开，带系统记录的进程退出原因。下次再有问题，用户贴这段就能定位，不用再猜。
- **查到并确认的一个卡死**：“导入邮箱”页一打开，GeckoView 的 GPU 进程就卡死，主线程等它等到超时（约 10 秒）后把它杀掉，期间整个模拟器不响应。
  这一页从第一版起就没在模拟器里开过，所以一直没发现。在实验分支上逐项排除（run 43574923756，已删）：怎么打开无关（直接用测试参数打开也卡）；
  去掉弹框的“圆角 + overflow:auto + max-height”就正常，加回来就卡。改成弹框不滚、外面的遮罩滚。真机上是否同样没有确认，但症状（白屏、卡死、闪退）对得上。
- **顺带**：批量导入邮箱时密码库每条都加密落盘（密钥在系统密钥库，每次跨进程）改成一批只落盘一次，免得卡住界面。
- **代价**：菜单从右上角的小弹窗变成整页；地址栏在内置页面显示期间藏起来。
- **仍然没验证**：真机。这一版是“换掉可疑的路 + 能取证”，不是“找到并证明了原因”。

### A-9 手机：人机验证诊断开关（2026-11-13，需求方：两端都过不了 Cloudflare 验证，选了“出诊断开关，逐项试”）

- **背景**：需求方的截图里 Turnstile 报 300030（验证组件在浏览器里执行出错 / 卡死），不是“判定为机器人”。电脑端只重启实例就好了（原因没定，见下）；手机端一直过不去。
  沙箱里测不了（机房 IP + 自动化本身就过不去），真机只有需求方有，所以先做开关让需求方自己定位，不凭猜测改默认值。
- **做法**：设置 → 人机验证诊断（只有手机显示）。11 个开关，每个对应 MaskTab 对内核做的一处改动，默认全开：
  `canvas` 画布噪声、`audio` 音频噪声、`hw` 核心数与屏幕高度、`lang` 语言（网页里和请求头）、`tz` 时区、
  `cfframe` 在 Cloudflare 验证框里也注入、`block` 认不出实例的请求一律拒绝、`ua` UA 里的安卓版本号按种子换、
  `tp` 跟踪保护、`fpp` 内核自带的指纹保护、`sw` 禁用 Service Worker。
  关掉的项记在设置 `fpOff` 里（核心服务只存不解释）；app 存一份在 `host.json`，因为内核偏好要在核心服务起来之前写好。
  生效时机不同（前七项刷新网页、`ua` / `tp` 新开标签页、`fpp` / `sw` 重启 app），页面上统一让用户点“重启 MaskTab”。
- **`block` 关掉时不直连**：认不出实例的网页请求改走“最近一个认得出实例的请求”所属实例的线路。只用于诊断：多个实例同时在用时可能走错实例的线路。
- **顺带记下被拒绝的请求**：内置扩展后台记“认不出实例”的请求（条数 + 最近 20 条的主机名、类型、来源），诊断页上能看，每种还进一次日志（随“复制诊断信息”带出来）。
  怀疑点：网页后台线程（Worker）发的请求在 GeckoView 里可能既没有标签页号、容器号也不准（bug 1948114），于是被拒绝，验证组件就卡死。这是手机独有的、和指纹无关的一条可疑线索。
- **已知的可疑点**（都没验证，等真机结果）：注入脚本改的时区 / 核心数 / 语言在 Worker 里改不到，两边一比就露馅；画布、音频噪声加了两层（内核指纹保护 + 注入脚本）；
  别的浏览器因为这类噪声出现过同样的验证死循环（cromite #2365、helium #249）。
- **电脑端没有改**：上游 fingerprint-chromium #88 报告 148.0.7778.215 在 Windows 上显卡伪装坏了、Cloudflare 验证无限循环，`--disable-spoofing=gpu` 可绕过；
  但需求方没关显卡伪装、只重启实例就能过了，所以不能确定就是它。需求方选了“先不改，再观察”。再出现时先看 `chrome://gpu` 的 Log Messages 里有没有
  `eglCreateContext: Requested version is not supported`，再关“显卡”那一项试。
- **现在的“CF 信誉 / 纯净度”不代表验证能不能过**（UI-3）：前者只是核心服务探得到 CF 那一路的出口；后者来自 ip.net.coffee，需求方的出口它给 0 风险、
  同时自己又检出“住宅代理、VPN 出口”，另一家（ippure）给 88。要改成“在实例自己的浏览器里真跑一次验证”，还没做。

### A-10 手机：网页语言改用内核原生设置，不再在页面里改 navigator.language（2026-11-15，2026-11-16 发布，未真机验证）

- **根因（沙箱复现）**：fp.js 用内容脚本改了主线程的 `navigator.language(s)`，Worker 里改不到（内容脚本进不了 Worker），
  主线程 `ko-KR` / Worker `en-US` 不一致，Cloudflare Turnstile 判 600010。官方火狐 160 + 同款注入，按项二分：只关“语言”就过，
  只改请求头不改 JS 也过，用内核偏好 `intl.accept_languages` 设成 ko-KR（Worker 一起变）也过；JS 改成和真实值相同也过——判的是“不一致”，不是改写本身。
  时区同样改不到 Worker（Worker 里仍是系统时区），这次没被判，但同一类风险。
- **为什么只在开代理时失败**：`expectTZ`（internal/core/proxyflow.go）在代理关掉时不给时区和语言，页面里就不改语言；开代理才按出口给 ko-KR。
- **为什么“诊断全关”也不过**：后台 `fpCfg` 走同步通道时漏了 `off`，fp.js 收不到关掉的项（异步通道带了，但同步先到、`__mtfpDone` 挡住了后来的）。已补上。
- **做法**：`Core.applyLocale()` 按当前实例调 `GeckoRuntimeSettings.setLocales`（内核原生，navigator / Worker / 请求头 / Intl 一起变）；
  fp.js 的语言改写默认关（`cfg.langJs` 才开）；后台不再改 Accept-Language。
  实例语言 ja-JP 时传 `[ja-JP, ja]`；回到系统语言时**显式传系统语言列表，不传 null**：GeckoView 160 的 `GeckoViewStartup` 收到 null 只重算 `intl.accept_languages`，
  不改 `Services.locale.requestedLocales`，Intl 默认语言会停在上一个实例上。安卓 FPP 默认项不含 JSLocale，不会把语言盖回 en-US。
- **代价**：GeckoRuntime 只有一份，后台实例的标签页也跟着当前实例的语言；GeckoView 会把系统语言追加在 `navigator.languages` 后面（computeAcceptLanguages）。
- **回退**：恢复 fp.js 语言段的条件、后台的 Accept-Language 监听，去掉 `applyLocale()` 调用。

### A-11 手机：运行中不再热换时区 / 语言；edgetunnel 不按 Workers 出口定时区（2026-11-16，随 v0.1.51 发布，未真机验证；后续见 A-12）

- **现象（真机 v0.1.50，edgetunnel + ProxyIP）**：CF 网站出口一直是 ProxyIP 210.138.37.53（日本），“普通网站”出口是 Workers 的 104.28.x（Cloudflare WARP 段），
  一会儿韩国一会儿日本。韩国时 Turnstile 过；变成日本后一直 300010，**彻底重启 app 才过**。
- **推断**：实例的时区跟的是“普通网站”那一路（启动日志时区 Asia/Seoul 只能来自 104.28.164.13），Workers 换机房 → 核心服务热换时区和语言 →
  手机上热换后某种只在进程内的状态和新值混在一起。沙箱（官方火狐 160 + 同款注入 + 韩/日语言包）实测：热换后新开 / 刷新的网页里，主线程和 Worker 的
  navigator.language、Intl 默认语言都正确更新，热换前后 Turnstile 都 PASS——所以**残留的不是网页能看到的语言 / 时区值**，而是会话级状态
  （会话 Cookie、TLS 会话、指纹保护的会话随机数、没刷新的网页里注入的旧时区）或核心服务 / mihomo 的状态。哪一样没定，等真机二分（work/turnstile-diag/REPORT-300010.md）。
- **做法**：宿主模式下实例运行中出口时区 / 语言变了，不再热换：网页继续用启动时的值（`LaunchedTZ` / `LaunchedLang`），标“需重启”，不断流；
  手机上“立即重启”重启整个 app（`/ui/restart`），因为 GeckoRuntime 一个进程只能建一次、内容进程没有接口单独重启。
  `expectTZ` 跟“普通网站”那一路时，如果那一路归属是 Cloudflare（WARP / Workers 出口）且有 CF 那一路，改用 CF 那一路。
- **代价**：手机上运行中改固定时区 / 语言、开关代理，也要重启 app 才生效。
- **回退**：恢复 `refreshTry` 里 `Caps().Live` 那一支的热换、`State` 里按 Launched 值给的分支。

### A-12 切换节点不改时区、不要求重启：时区按 ProxyIP 那一路、国家没变就沿用启动时的值（2026-11-16，v0.1.51，接着 A-11，未真机验证）

- **需求方**：只换入口时，时区不能变，也不应该要求重启；只有出口国家真的变了才提示需重启（不强制）；能做到切换节点不用重启更好。
- **做法**（`internal/core/proxyflow.go`）：
  - 定时区的那一路抽成 `tzSrc`：默认 CF 那一路（edgetunnel 下就是 ProxyIP）；设成“跟普通网站”时，那一路如果是 Cloudflare 自己的出站（Workers / WARP）且有 CF 那一路，仍用 CF 那一路（A-11）。只换入口不改 ProxyIP，所以不改这里的结果。`checks.go` 的“时区一致”也改用同一个函数（以前它没跟上 A-11 的规则）。
  - 实例启动时记下定时区那一路的国家和时区（`Runtime.launchedSrc`，不落盘、不进状态）。之后探到的出口**国家没变**就沿用启动时的时区（`expectTZPinned`）：同一个国家里换 ProxyIP（IP 库给了别的时区，例如美国东西海岸）不算变化，不标“需重启”。语言本来就按国家定，国家不变语言不变。
  - 这次没探到能定时区的那一路（两路都没有，或只探到 WARP 那一路）：判断不了，不算变化，放行，不标“需重启”。
  - 国家真的变了：手机上标“需重启”、**不断流**（A-11）；电脑上仍按 F-ISO-4 断流等重启（电脑内核的时区是启动参数，运行中改不了）。
  - 判定逻辑抽成纯函数 `judgeExit`，单测 `TestJudgeExitHotSwitch` 覆盖：Workers 出口变日本 / 香港（只换入口）、同国换 ProxyIP、只探到 WARP、出口换到美国、电脑同国换出口。
  - 换线路时 mihomo 上这个实例的旧连接本来就会关掉（`refreshTry` 里 `CloseConnections`），这次没改。
- **没做：自动清掉该实例 Cloudflare 的 Cookie（cf_clearance、__cf_bm）**。原因：
  - GeckoView 160 的 `StorageController` 只有“清整个容器”（`clearDataForSessionContext`，连登录一起清）和“按域名清全部容器”（`clearDataFromBaseDomain` / `clearDataFromHost`），没有“某个容器的某个 Cookie”。
  - 走内置扩展的 `browser.cookies`：它按 `storeId`（userContextId）、`firstPartyDomain`、`partitionKey` 过滤，而 GeckoView 的实例隔离用的是 `geckoViewSessionContextId`，不在过滤条件里——删的时候分不清是哪个实例的，可能删到别的实例；两个 Cookie 都是 HttpOnly，网页脚本也删不了。
  - 这两条都没法在沙箱里验证（没有 GeckoView）。按需求方“只做低风险、能验证的”，不做。真要做，要么等真机二分确认残留确实在这两个 Cookie 上，再试 `browser.cookies.getAll` 看返回的 `originAttributes` 带不带 `geckoViewSessionContextId`；要么让用户在三点菜单里手动“删除浏览数据”（会清登录）。
- **代价**：同一个国家里换出口时，网页的时区可能和 IP 库给的城市时区差几个小时（只在多时区国家）；“时区与出口所在地一致”那项检查会如实显示不一致。
- **回退**：`judgeExit` 里去掉 `unknown` 那一支，`expectTZPinned` 的 pin 传 nil。

### A-13 启动提速：网络检测先用上次的出口，其余放后台（2026-11-16，v0.1.51，真机未验证）

- **需求方**：手机启动页“加载订阅”“网络检测”很慢。要求启动只做必要的、并行、加超时；用缓存的订阅和上次的出口先进浏览器，其余后台补完；纯净度、CF 信誉不挡启动。
- **慢在哪（读代码 + 沙箱实测）**：
  - **订阅**：启动时**不下载**订阅（宿主模式只读核心服务存着的，代码里也没有定时刷新），这一步只有 app 自己加的 450 ms 停顿。看起来慢，是因为它前面的“启动核心服务”要等内置扩展装好才开始（模拟器上扩展要 6–12 秒），而它自己那一行在等待时不转圈。
  - **网络检测**（`Launch`）串着做：自动选线先现测一次延迟（每次最多 5 秒，最多两次）→ 两路出口探测（两个 trace 并行，12 秒超时）→ 两路归属**先后**各查一次（每个查询服务最多 12 秒，依次 ipinfo.io → ipwho.is → ip-api.com；结果只缓存在内存里，app 每次重开核心服务都是新进程，等于没有缓存）。
  - **实例就绪后又整套重来一遍**（`go a.refresh(id)`）：再选线、再测延迟、再探测、再查归属，而且这一遍期间主通道是 REJECT（`正在确认出口`）——启动页已经收起，刚恢复的标签页打不开。这是“慢”的大头。
  - 纯净度（`ipqEnsure`）本来就在后台；CF 信誉是从探测结果推出来的，不单独查。都不挡启动，这次没改。
- **做法**：
  - 手机：实例的线路（订阅 + 节点；edgetunnel 是订阅 + ProxyIP，入口不算）和上次一样、上次探到过能定时区的出口（3 天内）：**直接用上次的出口**定时区、语言，马上放行；后台 `verifyLaunch` 再探一次（**不断流**）：探到了按 A-12 判定（国家变了提示需重启），这次不通或只探到一路才走完整流程（断流、自动换线）。上次的出口存在 `state/lastexit.json`（实例 id → 线路、探测结果、时间）。
  - 归属查询结果落盘（`state/ipinfo.json`，7 天，最多 300 条），新进程读回来就不用再查；两路归属并行查；查询服务单个最多等 6 秒就换下一个。
  - 实例就绪后不再整套重来：启动时刚探过的，只 `afterLaunch`（放行 + 后台补测延迟、纯净度）。电脑版同样（启动后不再断流重探）。
  - `refreshTry` 里测延迟和出口探测改成并行。
  - app（`MainActivity.boot`）：核心服务和内置扩展同时开始启动，不再等扩展装好；去掉每步至少 450 ms 的停顿；最后一步的停留从 500 ms 改成 250 ms；每步日志带上距启动的毫秒数。
- **前后对比（沙箱实测，宿主模式核心服务 + 真 mihomo + ss 测试节点，节点前面加了每个方向 120 ms 的延迟，模拟手机到节点约 240 ms 往返；从核心服务就绪、开始启动实例算起）**：
  - 旧版（0.1.50）：实例就绪 3.1–3.3 秒，**网页能开 6.6–6.7 秒**（就绪后又断流重探约 3.4 秒）。
  - 新版，线路和上次一样（重开 app 的常见情况）：就绪、网页能开都是 **0.06 秒**；后台确认出口 1.2 秒后补上延迟。
  - 新版，没有上次的出口（第一次、换了线路）：就绪即能开网页 **3.2 秒**，延迟 4.4 秒时补上。
  - 另外 app 侧省掉：三步各 450 ms 的停顿；核心服务不再排在内置扩展之后（模拟器日志里扩展 6.5–12 秒、核心服务 1.2–1.9 秒，可以重叠）。真机上的绝对时间取决于网络，没测。
- **代价 / 风险**：
  - 上次的出口这次如果换了国家：网页先用旧时区开起来，一两秒后后台确认，提示需重启（A-11 / A-12，不断流）。
  - 上次的节点这次不通：先放行（mihomo 那边连不上，网页报错，不会直连，R-1 不破），后台确认失败后走完整流程断流、换线。
  - 启动后不再立即重探：探测和就绪之间出口如果刚好变了，要等下一次换线或手动“探测”才发现。
- **回退**：`Launch` 里不取 `cachedExitLocked`（`cached` 恒为 nil）、就绪后改回 `go a.refresh(id)`；app 的 `boot()` 恢复串行。

### UI-3 伪装度、纯净度、CF 信誉怎么算

- **伪装度** = 核心服务算的一致性检查（`internal/core/checks.go`，`/api/state` 里每个实例的 `checks`）通过的比例：经代理、出口可用、时区与出口一致、语言与出口国家一致、两路出口同国、CF 网站可达、出口纯净度 ≥ 50、设置已生效、UA 与内核一致、WebRTC 只走代理。
  出口还没探出来时判断不了的项不计入分母（显示“判断不了”），免得刚启动时显示一个吓人的低分。
- **纯净度** = 核心服务查好的出口 IP 纯净度（`st.ipq`，来源 ip.net.coffee，设置里可关）；查不到就画灰色空环，不编数字。
- **CF 信誉** = CF 网站那一路探不探得到出口：探到 = 良好；只有普通网站那一路 = 不可达；其余 = 未知。
- 两路出口在不同国家时，新标签页卡片和节点页出口卡片上给黄色提示。

### UI-5 下拉刷新

- **结论**：和官方 Chrome 一样：网页滚到最顶、往下拉，顶上出现圆形指示器，拉过 80dp 松手刷新，加载完收起（最多转 8 秒）。只在显示网页时生效（内置页面、新标签页不触发）。
- **做法**：`PullRefresh`（FrameLayout，包着 GeckoView）拦截手势的条件是三个同时成立：
  ① 页面在顶部（`GeckoSession.ScrollDelegate` 报的 scrollY = 0）；
  ② Gecko（APZ）对这次按下的判断：没被网页自己接手（不是 `INPUT_RESULT_HANDLED_CONTENT`：preventDefault、里层可滚动区域）、页面不能再往上滚（没有 `SCROLLABLE_FLAG_TOP`）、允许纵向越界（CSS `overscroll-behavior` 没关）——`GeckoView.onTouchEventForDetailResult` 给的 `InputResultDetail`，和 Fenix 的做法一样；
  ③ 手指明显向下（超过 touch slop，纵向是横向的 1.5 倍）。拦截后网页收到 CANCEL，之后由指示器接手。没用 SwipeRefreshLayout：项目不依赖 AndroidX（A-5）。
- **证据**：CI 模拟器冒烟里在 example.com 顶部往下拉要触发刷新、往上滑不能触发。真机、长页面、网页自己有下拉手势的站点没有测。

### UI-6 Windows 任务栏图标（A 方案：浏览器图标右下角加彩色编号角标）没有做

- **2026-11-16 更正**：这一条的结论已经作废，任务栏图标做了，见 UI-14。下面“外面改了会被覆盖”“CI 截图看不出任务栏”两点当时没有实测，实测都不成立。原文保留作记录。
- **结论**：没做，留作后续。
- **原因**：
  - 任务栏上的窗口属于内核进程（fingerprint-chromium 的 chrome.exe），不属于核心服务。给它加角标要调 `ITaskbarList3::SetOverlayIcon(窗口句柄, 图标)`；这个接口按文档只对调用者自己进程的窗口可靠，跨进程给别人的窗口设角标不保证生效。
  - 另一条路是改窗口属性（`SHGetPropertyStoreForWindow` 写 `PKEY_AppUserModel_RelaunchIconResource` / 改 AppUserModelID）：Chromium 自己会按用户目录设置 AppUserModelID 并在窗口创建时写这些属性，外面改了会被覆盖，也会打乱任务栏分组。
  - 现有代码里没有任何任务栏 / AppUserModel / .ico 的实现可以接着做；没有真实 Windows 桌面验证（CI 的 Windows Server 截图看不出任务栏角标是否稳定）。
- **影响**：任务栏上各实例仍是同一个浏览器图标，要靠窗口里的工具栏头像（M-2）区分。要做的话，比较稳的办法是改内核（在 Chromium 里按 `--fingerprint` 种子 / 实例编号画角标），不是在核心服务里做。

### UI-7 弹框不滚，遮罩滚（“圆角 + overflow 滚动”在模拟器里卡死 GPU，第二次踩到）

- **现象**：分支 `ui/chrome` 第一次推送（7901253）的模拟器冒烟（Android run 43622971231）里，打开“导入邮箱”后 GeckoView 的 GPU 进程卡死被杀（logcat：`Killing GPU process due to IPC reply timeout`），之后每张截图都截不出来，整个脚本超时。
- **原因**：重写 `ui.css`（UI-1）时，`.dlg`、`.modal`、`.sheet` 又写成了“圆角 + `overflow-y:auto` + `max-height`”。这正是 A-8 里用 run 43574923756 逐项排除定位到的组合，旧 `android/ext/app.css` 里写着这条规矩，但重写时这条注释没有跟过来。
- **做法**：遮罩 `.scrim` 自己滚（`overflow-y:auto`，纵向 flex），弹框不滚也不限高：`.dlg` / `.modal` 用 `margin:auto` 居中（比屏幕高时 auto 归零、从顶上排，遮罩滚）；`.sheet` 用 `margin-top:auto` 贴底（电脑上 `margin:auto` 居中）。规矩写回 `ui.css` 的注释。
  全仓库搜过：别的可滚动容器（`.chips`、`.accs`、`.drawer`、`.pnav`、电脑弹窗的 `.insts`）都没有圆角；输入框 / 文本框不算（以前实测不受影响）。
- **防止第三次**：`preview-pages.mjs` 新增检查：每个预览页面和打开的对话框里不能有“圆角 + overflow:auto/scroll”的元素；矮屏（412×420）上的导入邮箱弹框必须是遮罩滚、弹框本身不滚不截断。用旧的 `ui.css` 跑，这两项都会失败。
- **同一次 run 里的另两处失败**（不是界面问题，是测试找错了控件 / 参数被吃掉）：

### UI-8 左右不被遮挡：启动页按左右 insets 留边，页面处理左右安全区（2026-11-16，v0.1.51）

- **现象（用户截图，vivo V2419A，Android 17）**：启动页左边的绿色勾被裁掉一半，右边“mihomo v1.19.3…”被截断。
- **原因**：不是 edge-to-edge 的 insets，是启动页的宽度算错：每一行固定 `min(320dp, 屏宽 - 48dp)`，而列两边各留 32dp。屏幕窄于 384dp 时（把“显示大小”调大的手机，这台约 360dp），行比列宽 16dp，被列的内边距裁掉（`clipToPadding`）。截图里裁掉的位置正好是 32dp。
  另外启动页以前只拿了上下 insets，没拿左右的（横屏刘海、三键导航时会被挡）。
- **做法**：
  - 启动页（`StartupView`）：行宽跟着列走（`match_parent`），列的左右留边 = 左右 insets + max(24dp, 居中留白)，内容最宽 320dp；屏幕尺寸变了重新算。
  - 三点菜单的宽度扣掉左右 insets。其余原生浮层本来就按左右 insets 留边（`fitOverlay`），网页 / 内置页面所在的那一列也一直按左右 insets 留边（UI-4）。
  - 内置页面：`viewport-fit=cover`；`ui.css` 里 `body`、全屏遮罩、抽屉按 `env(safe-area-inset-left/right)` 留边，悬浮按钮、提示条跟着让开。手机上 app 已经把网页区域让开了，`env()` 一般是 0；电脑上恒为 0。
  - 顺带修了一处真的横向溢出：实例管理（手机精简版卡片）在 320 / 360 宽时卡片撑出屏幕右边 50px，最右边的开关按钮被挡住（`grid-template-columns: 1fr` 的下限是卡片的最小内容宽度）。改成 `minmax(0, 1fr)`。
- **防再犯**：`preview-pages.mjs` 新增两项：320 / 360 宽下每一页不能横向溢出、不能有元素伸出屏幕左右边；模拟左右各 40px 的安全区，节点页内容要让开。
- **没验证**：启动页的改动是 Kotlin，沙箱编译不了，靠 CI 构建和模拟器截图；真机（vivo 那台）没看过。网页（网站）本身的左右安全区由网站自己决定，app 这边是整列让开。

### UI-13 电脑弹窗：一屏看到更多实例、打字就能切换（2026-11-16 需求方截图：“实例只能看到 3 个，也不能拉伸，切换好麻烦”）

弹窗的高度是浏览器定死的（最高 600），用户也拉不大。以前四个入口一行一个占了 184，下面只剩三个实例的位置。改法：

1. **四个入口排成两列**（账号管理 / 节点与出口 / 指纹与伪装 / 录入登录），省出两行；“节点与出口”那一格只留国旗（国家名在上面的卡片里看得到 IP 和国旗）。只在电脑弹窗里这样排；手机的页面版菜单还是一行一个。
2. **列表自己挑排法**：两行一个（名字 + 出口）放得下全部就用它（现在最多 6 个）；放不下改成一行一个的紧凑排法（小头像、名字、右边国旗，IP 在悬停提示里），最多 8 个不用滚；再多才滚（带搜索框时一屏 7 个）。
3. **搜索框只在超过 8 个时常驻**。不管它在不在，弹窗里**直接打字就是搜索**（不用先点）；输入数字时按编号排（编号正好是它的最前，其次是以它开头的）；回车打开 / 切到第一个；↓↑ 在列表里挪动。配上已有的 `Alt+P`（打开弹窗），可以全程不碰鼠标：`Alt+P` → 打编号 → 回车。
4. **开着的实例排在休眠的前面**（和实例页的两组一个次序），组内还是拖出来的次序。

没有做的：把弹窗做宽成两栏（左边当前实例、右边列表）。能多放几个，但和演示定稿的样子差得远，先不动。

检查：`preview-pages.mjs` 加 5 项（6 个 / 8 个别的实例一屏全看得到；入口两列、开着的在前；打字出搜索并按编号排；↓↑ 和回车）。

补（2026-11-16，随 N-2 一起）：**打字时焦点会丢。** 后台刷新状态（`load`）是异步的，取回状态后的重画如果正好落在用户按下第一个字之后，
搜索框被换成新的、焦点没了，接着打的字、↓、回车都没有反应。CI 里“直接打字…”“↓↑…”两项因此失败过（运行 43877532143），沙箱里机器忙时也失败过。
改法（`popup.js`）：重画前记下焦点是不是在搜索框里和光标位置，重画后放回去；后台刷新取回状态时用户已经在输入框里就不重画（`load(true)`）。
验证：三个死循环占满 CPU 时，改之前 2 次里失败 1 次，改之后 4 次全过。这是概率性的，不算证明。

### UI-14 Windows 任务栏：每个实例是自己颜色的图标（2026-11-16，需求方截图：四个一模一样的图标，“任务栏不会区分，可以按照颜色区分”）

### N-3 在线更新：电脑、手机都从 GitHub Releases 更新（2026-11-16，需求方：“手机电脑都可以通过 github 在线更新”）

- **结论**：设置 → 组件与更新 里有“检查更新 / 更新 / 安装”。两端是同一份逻辑（核心服务查版本、下载、校验），只有最后“安装”这一步各做各的。
  有新版本时新标签页搜索框下面有一行提示，设置首页那一行也写着；可以点“这一版先不更新”。默认每 6 小时自动查一次（只查，不自动下载、不自动安装），可以关。
- **查版本**（`internal/update`）：先问接口 `api.github.com/repos/halou367/masktab/releases/latest`（带每个文件的 SHA-256）；
  接口不通或者被限流（没登录每个 IP 每小时 60 次，多人共用一个出口时会用完）就走网页：`github.com/…/releases/latest` 的跳转地址里有版本号，
  校验值读同一个版本里的 `SHA256SUMS.txt`（发布流程生成，0.1.72 及以前的版本没有这个文件）。先直连，再走本机正在用的代理。
  下载地址自己拼（`…/releases/download/v<版本>/<文件名>`），不用接口回的地址。自己编译的版本（版本号不是数字）不提示更新。
- **下载**（`internal/core/update.go`）：和下载内核同一套（`kernel.Fetch`）：直连 → 本机代理 → 镜像站，断点续传，下完校验 SHA-256，不对就丢掉。
  镜像站只在知道 SHA-256 时才用（内容以校验值为准，不信镜像站）。文件放 `<数据>/update/<版本>-<文件名>`；下好之后再检查会认出来，不重下；更新完下次启动时清掉。
- **安装**：
  - 电脑（Windows）：核心服务再校验一遍，留一个“恢复一次”的记号，运行 `MaskTab-Setup.exe /S /RELAUNCH /D=<现在的安装目录>`，然后关掉全部窗口退出；
    安装程序换掉 `masktab.exe`（数据、内核不动），带 `/RELAUNCH` 时装完把 MaskTab 重新打开；重新打开时把更新前开着的实例都开回来（不看“启动时恢复”设置）。
    下载的是普通安装包（约 3 MB），不含内核。
  - 手机（安卓）：核心服务校验过才把文件路径给 app（`GET /api/update/file`），app 用系统的 `PackageInstaller` 会话安装（`Updater.kt`，不需要 FileProvider / AndroidX）。
    第一次要用户在系统页面里允许“MaskTab 安装应用”（权限 `REQUEST_INSTALL_PACKAGES`），之后系统弹“要更新这个应用吗”，确认后安装。
    装好的那一刻系统会把 MaskTab 关掉，**不会自动再打开**（系统不允许应用在后台自己弹出来），要自己点图标；数据不动。没装成（取消、空间不够、被手机管家拦）时原因写在更新页上。
  - 其它系统（自己编译的 Linux 版）：只提示，给发布页的链接。
- **发布流程跟着改的**（`ci.yml`）：发布里多一个 `SHA256SUMS.txt`；发布说明最前面是“这一版的改动”（上一个版本到现在的提交标题，
  以“CI：”“文档：”“测试：”开头的不列），用一行 `---` 和安装说明隔开，更新页只显示这一段。**所以提交标题要写成用户看得懂的话。**
- **证据**：
  - 单元测试：`internal/update`（接口、网页两条路，限流，版本比较）、`internal/core/update_test.go`（检查、下载、校验不符丢弃、文件被动过不给、外壳报告）。
  - 真的 GitHub（v0.1.76 发出来之后查的）：接口、网页两条路都查到 0.1.76，电脑安装包和手机 APK 的 SHA-256 两条路一致。
  - Windows（CI run 43911026318，假的 GitHub = `scripts/fake-github.mjs`，版本写成 0.1.99999）：查到 → 下载校验 → 旧进程退出 → 安装程序运行 → 重新打开 → 更新前开着的实例恢复 → 能正常退出，9 项全过，截图 `8-after-online-update.png`。
  - 安卓模拟器（Android run 43908237578，API 35，假的 GitHub = 测试里的静态文件服务）：查到 → 下载校验（134 MB）→ 没有许可时打开系统的“安装未知应用”页 → 系统弹出确认 → 点“Update”→ 系统装好 → 重新打开四个实例都在，截图 `20-update-available.png` … `25-update-reopened.png`。
  - 页面检查（`preview-pages.mjs`）：更新页的各个阶段（有新版本 / 下载中 / 已下载 / 出错 / 已是最新）、两种宽度、电脑深浅两种、新标签页的提示，共 9 项。
- **没验证的**：真手机（尤其是国产系统的安装拦截、“纯净模式”）；真的 Windows 10 / 11 上杀毒软件对静默安装的反应；装在需要管理员权限的目录时（默认装在用户目录，不需要）；
  大陆网络下直连 GitHub 不通时靠代理 / 镜像站下载的实际速度；安卓 8 ~ 13 上的系统安装界面（模拟器只测了 15）。
- **已知的限制**：
  - 0.1.72 及以前的版本里没有这个功能，要先手动装一次带这个功能的版本，之后才能在线更新。
  - 安装包没有单独的签名验证，可信度 = GitHub 的 HTTPS + 发布里的 SHA-256；安卓另有系统的签名校验（签名不一致系统拒绝安装）。
  - 手机上下载的是整个 APK（约 130 MB，内核在里面），没有增量更新。

#### N-3 补充：更新先走浏览器的节点，都不通再直连（2026-11-17，需求方：“更新默认就走代理也就是浏览器节点都不通再直连”）

- **结论**：查版本、下载安装包的次序从“直连 → 本机代理 → 镜像站”改成 **节点 → 直连 → 本机代理 → 镜像站**（`updateSources` / `nodeSources`，`internal/core/update.go`）。
  “节点”有两种，依次排：
  1. **开着的实例正在用的线路**：代理开着、出口探得到的实例，经它的探测通道出去（和它的网页同一条线路，不受断流影响）；延迟低的在前，最多两条。界面和日志里写“#3 的节点”。
  2. **订阅里测过是通的节点**：按延迟取前三个，现测一次（每个最多 4 秒），第一个还通的接到“更新通道”上，算一条，写“节点 <名字>”。
     没有实例开着、或者开着的都是直连时靠它。更新通道是代理内核里多出来的一个本机端口（入站 `in-upd`、策略组 `g-upd`，能切到任何一个节点），
     平时停在 REJECT，查完 / 下完切回 REJECT（本机别的程序借不了它走节点）；中途配置重载会把选择补回去。
- **两种都没有**（没加订阅、节点都没测过或者都不通）时和以前一样，从直连开始。前一条不通、或者下载太慢，自动换下一条，断点续传照旧。
- **要知道的**：这样查版本、下安装包的请求是从节点的出口 IP 发出去的，用的是节点的流量（普通安装包约 3 MB，手机 APK 一百多 MB）。
  多人共用的出口上 GitHub 接口容易被限流，那时自动走网页那条路（N-3 原有的）。检查更新的总时限从 45 秒放到 90 秒（节点不通时每条要等一阵才轮到直连）。
- **没改的**：下载内核、拉订阅还是原来的次序（直连 → 本机代理 → 镜像）——第一次装的时候还没有节点可用；需求方这次也只说了更新。
- **证据**：
  - 单元测试 `TestUpdateViaNode`：次序（两种节点各自的挑法、排法，后面跟着直连）；经一个假的 socks5 代理真的查到版本、下完安装包并校验通过（代理数得到连接）；节点不通时落到直连。
  - 实测 `scripts/update-node-e2e.mjs`（Linux，真的核心服务 + 真的 mihomo 1.19，节点 / 发布页 / 订阅是本机假服务）：没有实例开着时检查更新“经 节点 e2e-live”，
    假节点上数得到连接；查完以后经更新通道连不出去；把假节点关掉再查，落到“直连”。这个脚本没接进 CI，动这一块时手动跑。
  - **没验证**：真的节点 + 真的 GitHub；Windows 真机上下载、安装整条路走节点；手机；第 1 种（借开着的实例）只有单元测试，没有在真的 mihomo 上跑过。

### F-HEAL 订阅 / 节点没了也打得开、改得了；编号可以改（2026-11-17，需求方：“订阅删除后实例无法打开也无法修改，形成死循环；实例删除后序号也没法修正”）

- **原来的毛病**（一环扣一环）：
  1. 删订阅时，用它的实例的 `subscriptionId` 被清空，或者被指到另一个订阅上但节点、入口还是旧订阅的（对不上）。
  2. 电脑版启动实例时代理这边只要不行（没选订阅、节点不在了、探不出出口），就“没能打开”（PLAN 的 F-INST-4）。
  3. “节点与出口”只在实例自己的窗口里（工具栏弹窗、它的设置页）。窗口开不起来，就没有地方改。
  4. 编号只增不减：删过实例以后编号有空缺，没有任何办法改。
- **现在的规矩**：
  1. **窗口一定打得开**。只有“没有浏览器内核”“代理内核没起来”两种情况拒绝（后一种放行就是真实 IP，硬规则 R-1），原因写在实例上，组件准备好以后自己消掉。
     代理这边不行时窗口照开，主通道停在 REJECT，原因和“怎么修”写在新标签页、节点面板、实例卡片上。
  2. **不回落直连，也不悄悄换节点**（R-1 不变）：
     - 自动的那一半（自动选出口 / 入口 / 节点）坏了就重新挑。
     - 用户手动钉死的节点 / 出口坏了：不换，只提示。
     - 整个订阅没了：改用默认订阅（没有默认就用第一个），出口、入口都改成自动；一个订阅都没有就留着“代理开、没有线路”，断网等新订阅，加了新订阅自动接上。
     - 程序替用户改过什么，记在 `rt.fixed` 里显示出来，点“知道了”或自己改一次代理后收起。
  3. **不开窗口也能改**：实例管理 → 点实例 → “节点与出口”，进去是完整的节点面板，对着这个实例（路由 `node/<实例 id>`），里面能直接打开 / 关闭它。
  4. **出口确认之前仍然一个字节也出不去**（F-INST-4 要防的事没有放松）：窗口是断着网开的；用户选好线路后由平时的流程现探出口，
     出口的时区和窗口启动时的不一样就继续断着并提示“需重启”，不会带着错的时区上网。线路和上次一样时窗口按上次那个出口的时区启动，线路恢复后多半不用重启。
  5. **编号**：新实例用最小的空号（1 到 9999）；抽屉里点编号可以改，和别人撞号就对调；实例页顶栏“整理编号”一键排成 1、2、3…（有空缺时才出现）。
     编号只是名字：数据目录、账号、Cookie 都按实例 id 记，不受影响。运行中的窗口标题里是旧编号，提示重启（`needRestart: appearance`）。
  6. **订阅可以改名、改地址**（`PATCH /api/subscriptions/{id}`）：订阅还是这一个，用它的实例不用重选；新地址先拉一遍，拉不下来不改。
     删订阅前写明哪些实例在用、删了以后会怎样。
  7. 顺手修的自洽问题：
     - 探出口的几秒里点了关闭 / 删除，探完照样把窗口拉起来（删掉的实例又冒出一个窗口）→ 启动带编号，被叫停就收手；“正在打开”时卡片上有“取消”。
     - 删出口、删地址库里的地址后，钉在它上面的实例指向空处 → 自动的重挑，手动的提示；接口返回受影响的个数。
     - 默认订阅指着已删的订阅 → 修正；设默认订阅时不认识的 id 拒绝。
     - 没有订阅时把代理从关拨到开 → 拒绝并说明（已经开着的不动）。
     - 启动时把上面这些全查一遍（`healAllLocked`），旧数据里已经坏掉的也修。
- **代码**：`internal/core/heal.go`（规则都在这里）、`launch.go`（`Launch`）、`subs.go`、`api.go`、`proxyflow.go`（断网原因的措辞）；
  界面 `panel.js`（`panel.target`）、`instances.js`（抽屉里的“节点与出口”、改编号、整理编号）、`pages.js`（订阅菜单）、`ntp.js`（断网提示）。
- **证据**：
  - `internal/core/heal_test.go` 9 项（删订阅两种顺序、节点 / 入口不在了、删出口、没订阅开代理、编号、删实例、接口）。
  - `scripts/smoke.mjs` 第 6c 段，**真内核 + 真核心服务**（本地 Linux 无头，CI 的 Windows / Linux 也跑）：节点全不通 → 窗口打开且断着网；删掉唯一的订阅 → 还能打开，写明“还没有订阅”；
    再加订阅 → 自动接上；改名改地址 id 不变；改编号、对调、整理、空号复用。本地 42 项全过。
  - `android/scripts/preview-pages.mjs` 加 21 项（手机、电脑两套界面的点按流程），共 144 项通过。
- **没验证的**：真 Windows 窗口、真手机；“断着网开窗 → 在窗口里选好能用的线路 → 放行 / 提示重启”这一段要有真能用的订阅才能走完，沙箱里没有，只确认了断网那一半。

### P-1 改动分级、检查分层、发版不跟着推送走（2026-11-17，需求方：“小问题改了一个半小时”“长期看整个项目的修改怎么高效起来”）

- **原因**：项目不大，但每次改动不论大小都付同样的固定成本——重新摸一遍项目（没有地图，文档是按时间记的流水账）、手工恢复环境、页面检查一跑就是全套两分多钟、推一次等一轮十五分钟的 CI、每次推到 `main` 都发一版。
- **现在的规矩**（全文在 `AGENTS.md`“改动分三级”）：
  1. 改动分小 / 中 / 大三级，按级别验证；小改动不跑全套、不写长文档。
  2. 检查分四层，一个入口 `scripts/check.sh`：`fast`（秒级）、`pages [段]`（页面，分 13 段，可以只跑一段；全跑时五个进程同时跑）、`ext`、`smoke`。CI 跑的是同一个脚本，本地过了 CI 就该过。
  3. 每次推送 CI 只跑快检查、页面检查、Linux 冒烟；只改文档的推送不跑。Windows 安装包、安卓构建和模拟器只在**手动触发**时跑。
  4. **发版 = 手动触发 CI**（`scripts/release.sh`，或 Actions 页面上点 Run workflow），在 `main` 上、全套通过才发。不想发版只想跑全套：`scripts/release.sh --check`。
  5. 环境一条命令恢复：`scripts/dev-setup.sh`（装在 `~/.cache/masktab-dev`，不进仓库）。
  6. 项目地图 `docs/MAP.md`，一页；结构变了改它。
- **没变的**：D-3（一个版本号、电脑手机一起发、一项不过就不发）；版本号还是 `0.1.<CI 运行序号>`，标签 `v0.1.*`、`SHA256SUMS.txt` 不变，在线更新（N-3）不受影响。四条硬规则和它们的检查一条没少，只是从“每次都跑”变成“动到了才跑 + 发版前一定跑”。
- **代价**：
  - Windows 专有的问题（安装程序、任务栏、真窗口）和安卓外壳的问题，不再是每次推送都能发现，最晚到发版前那一轮才发现。所以动了这些地方的改动算“大改动”，合并前要跑 `scripts/release.sh --check`。
  - 版本号跳得更厉害（每次推送都占一个运行序号）。只保证越来越大。
  - 小改动不会马上有版本号，用户要等下一次发版才拿得到。
- **实测**（沙箱，2 核，2026-11-17）：恢复环境 25 秒（不含内核）；`fast` 第一次 44 秒（要编译），之后 3 ~ 6 秒；`pages` 全套 35 秒（原来一个进程 132 秒），单段 `heal` 15 秒；`ext` 34 秒；`smoke` 124 秒。
  CI：推送一轮 3 分 45 秒（快检查 36 秒、页面 1 分、Linux 冒烟 3 分 45 秒，三样同时跑；原来 10 ~ 15 分钟）；手动触发的全套 12 分钟左右（Windows 10 分半、安卓构建 2 分 + 模拟器 10 分）。在分支上用“只跑全套不发版”验过一轮，全过、没有发版。
- **顺带发现的两个洞**：
  - 界面脚本的语法检查以前**对模块不管用**：`node --check 文件` 遇到带 `import` 的文件，Node 22 上有语法错也返回 0（实测）。也就是 `ui.js`、`panel.js`、`pages.js` 这些一直没被查到。现在模块一律按模块从标准输入查，故意写错四种（模块、网页脚本、Go 测试、只在 Windows 上的 vet 错）都验过能拦住。
  - 页面检查脚本中途超时只剩一句“Timeout”，已经跑完的结果全丢；现在会把跑完的和断在哪一段打出来。
- **还欠着的结构整理**列在 `docs/MAP.md` 末尾，改到哪一块做哪一块，不单独停下来重写。
- **回退**：把 `ci.yml` 里 `windows`、`android`、`release` 三个 job 的 `if` 改回去（`release` / `android` 用 `github.ref == 'refs/heads/main'`，`windows` 去掉 `if`）。

### UI-15 合并窗口：各实例的窗口叠在一个位置，顶上一排实例颜色的标签（2026-11-17，需求方：“多个实例的窗口合并到一个窗口，顶部变成双色标签”）

- **能做到什么、做不到什么**：每个实例仍然是自己的浏览器进程（指纹、代理、“没代理就断网”都在进程这一层，R-1…R-4 不动），所以不同实例的网页标签页进不了同一排标签。做的是**叠放切换**：所有实例的窗口摆在同一个位置、同样大小，只显示一个；它顶上多一排“实例标签”，每个实例一个，颜色是实例自己的颜色，点哪个显示哪个。看起来是一个窗口、两排标签（上面一排是实例，下面一排是这个实例自己的网页）。
- **没选的做法**：把各实例的窗口真的塞进一个外壳窗口当子窗口。输入法候选框、下拉菜单、全屏、不同缩放比的屏幕都容易出毛病，放弃。
- **范围**：只有 Windows 桌面版。~~默认关~~ **2026-11-18 改成默认开**（需求方：“改成默认开启，合并两个都开启默认启用就好了”；见本节末尾“默认开”），设置 →「启动」→「合并窗口」（`mergeWindows`）。手机、macOS、Linux 没有这一行。
- **代码**：
  - `internal/tabbar`：只认识窗口，不认识实例和代理。`tabbar.go`（排版、命中、位置计算，可在任何系统上测）、`render.go`（画标签）、`bar_windows.go`（Windows 窗口操作）、`bar_other.go`（别的系统上的空实现）。
  - `internal/core/mergewin.go`：把“哪些实例在运行、各是哪个进程、什么颜色”交给它，响应三个动作：关闭（= 停实例）、打开一个没在运行的实例、新建实例。
- **规矩**：
  - 标签 = 正在运行的实例，按编号排。左键切换，× 或中键关闭这个实例，「＋」列出没在运行的实例和“新建实例”。
  - 新开的实例、别处让它到前面的实例（比如头像菜单里点它），自动成为当前标签。当前实例关了，换到旁边那个，位置不变。
  - 拖窗口、改大小，实例栏跟着；切换标签时下一个窗口摆到同样的位置和大小。
  - **最大化**：浏览器自己的最大化不给实例栏留地方，所以改成“铺满屏幕可用区域、顶上留出实例栏”。再点一次最大化（或双击实例栏空白处）还原。F11 全屏、视频全屏时实例栏收起。
  - 最小化时实例栏一起收起，还原时一起回来。
  - 实例栏的底色是当前窗口标题栏的颜色（从屏幕上量，量不到时按实例颜色估），压住窗口顶上 5 像素，看起来是一整块。实例颜色和标题栏一样时（黄色这类浅色）选中的标签用浅一档。
  - 关掉开关、退出 MaskTab：藏着的窗口全部放出来，不再管。
  - 藏着的实例窗口在任务栏上没有按钮（任务栏上只有当前这一个），要切换用实例栏。
- **已知的限制**：
  - 一个实例开了多个浏览器窗口时，只有一个在合并里，其余的照常单独显示。
  - 网页标签页不能在实例之间拖。
  - 核心服务被强行结束（不是正常退出）时，藏着的窗口不会自己出来；下次启动这个实例时会被当作遗留进程清掉重开。
- **证据（2026-11-17，需求方的 Windows 11 实机，开发版 + 单独的测试数据，没碰正在用的 MaskTab）**：三个实例合并显示；点标签切换；× 和中键关闭；「＋」菜单打开没在运行的实例；双击空白铺满 / 还原；系统最大化两次 = 铺满 / 还原；最小化 / 还原；移动窗口后实例栏跟随；关开关后两个窗口都显示、再开又合并；退出时窗口全部关闭。截图 `shots/merge-windows.png`（会话里）。
- **真机上找到并修掉的**：从最小化还原的一瞬间系统已报告“没最小化”但窗口位置还是 (-32000, -32000)，照它摆位置会把窗口丢到屏幕外；按大小排除画中画窗口时把缩得很小的浏览器窗口也排除了（改成排除“总在最前”的窗口）；Windows 图形程序没有标准错误输出，`io.MultiWriter(os.Stderr, 日志文件)` 第一个写失败就不写文件了，日志一直是空的；点 #2 的标签却跳到 #3（藏起原来的前台窗口时系统自己另挑了一个藏着的实例窗口当前台，实例栏以为“它被叫到前面了”就跟过去了：改成先把目标设成前台再藏原来的，并且刚换完标签的 1.5 秒里不跟）。
- **没验证**：用真鼠标点标签以后窗口是不是稳稳留在最前面（测试是发消息点的，Windows 对“谁能把窗口设到前台”的限制和真点击不一样；当前标签对不对已经验证，前后顺序没法这样验证）；用真鼠标拖实例栏空白处移动窗口（测试是发消息点的，拖动没法这样测）；两块屏幕缩放比不同时；输入法、网页里的下拉菜单在切换后的表现；窗口贴边分屏（Win+←）；实例很多（标签挤到最窄）时的样子。


- **默认开（2026-11-18）**：`mergeWindows`、`mergeCompact` 默认都是 true（`model.DefaultSettings`）。起因：需求方装了 0.1.120 说“合并功能并没有效果”——功能在，开关默认关着，没人知道要去开。
  老版本升上来的（设置文件里没有这两项，或者以前是关的——以前关着是不写进文件的，分不出来）也按默认的开；之后手动关掉的会存住
  （这两项去掉了 `omitempty`：默认值是 true 的开关，false 必须真的写进文件）。证据：`TestMergeDefaultsPersist`；
  Windows 冒烟测试先查默认是开的，再开着查一次“实例栏起来了、两个窗口并在一组”，其余检查关着跑（它们是按“每个实例一个自己的窗口”写的，比如任务栏上各有一个图标）。
  **仍然没验证的**照旧（真鼠标拖出 / 并入、最大化、其它缩放、Windows 10），现在它们是默认行为了，出问题先到 设置 → 启动 里关掉。

### UI-16 合并窗口可以分成几组：标签拖出来单独一个窗口，拖到另一组的栏上并进去（2026-11-17，需求方：“希望顶部窗口可以和标签一样拖拽出来变成独立的实例，也可以拖拽合并成多个实例”“边缘有点问题”）

- **要不要重新编译内核**：不用。实例栏、拖出去、并进来，都是在浏览器窗口外面摆窗口，内核一行不改。**只有**“把实例标签和浏览器自己那排网页标签做成同一排”才必须改内核源码重新编译（每个实例是自己的进程和用户目录，标签栏画在各自进程里）；没做，要做得另起一件事。
- **规矩**（在 UI-15 之上）：
  - 一“组” = 叠在一起的几个实例窗口 + 它们自己的实例栏。可以有好几组；只有一个实例的组也有栏（不然没处抓着拖回去）。
  - 按住一个标签拖：鼠标离开栏 14 像素以上（`tabbar.Left`），这个实例从组里出来自成一组，窗口跟着鼠标走，抓的那一点一直在鼠标底下（`tabbar.Carry`）。
  - 拖着的时候鼠标到了另一组的栏上（上下各放宽 8 像素，`tabbar.Over`），那一栏变亮；这时松手就并进那一组，并且成为当前标签。
  - 只有一个标签的组，拖标签 = 拖整个窗口，同样可以并进别的组。
  - 新启动的实例进哪一组：30 秒内在哪一组点过「＋」就进哪一组；否则进最近用过的那一组。
  - 关掉开关再打开、重启 MaskTab：回到一组（分组不存盘）。
- **边缘**（需求方截图里箭头指的地方）：原来实例栏没有边线、下面的浏览器窗口有一圈 1 像素灰边，接缝处两侧各露出一小截。现在把当前窗口的边线改成和栏一样的颜色（`DWMWA_BORDER_COLOR`，只有 Windows 11 有；Windows 10 上不改），栏的两端往下多画 3 像素盖住接缝（`tabbar.Ears`）。放手时边线改回系统默认。
- **代码**：`internal/tabbar/bar_windows.go`（`mgr` 管几组，`group` 是一组；`detach` / `merge` / `startDrag` / `dragMove` / `endDrag`）、`paint_windows.go`（画）、`win_windows.go`（窗口操作）。能在任何系统上测的计算在 `tabbar.go` / `render.go`（`TestDragOutAndOver`、`TestCarry`、`TestEars`）。
- **真机上找到并修掉的**：
  - 拆组、并组做到一半时，系统的“前台窗口变了”“窗口挪了”通知插进来，把做到一半的状态拿去对了一遍账，拖出来的窗口落点偏了几十到上百像素。现在处理一件事的当中来的通知先记下，做完再对一遍（`enter` / `leave`）。
  - 测试脚本的坑（不是产品的问题）：PowerShell 里函数名 `LP` 是 `Out-Printer` 的别名、`$r` 和 `$R` 是同一个变量；模拟点击不带屏幕坐标时栏会去问真鼠标在哪，以为被拖出去了。
- **证据（2026-11-17，需求方的 Windows 11 实机，开发版 + 单独的测试数据）**：三个实例起来是一组；把中间的标签拖出去 → 两组，落点和鼠标位置对得上（差值就是抓的那一点）；拖到另一组的栏上停住 → 那一栏变亮（`drop`），松手 → 回到一组并成为当前标签；一个标签的组关掉 → 这一组消失，另一组不受影响；两组时新启动的实例进了最近用过的那一组；开关关掉 → 三个窗口都放出来，再打开 → 重新合成一组；屏幕实拍（不是窗口截图）左右两侧从栏到窗口是一个颜色，没有灰边。
- **没验证**：**用真鼠标拖**（测试是发消息模拟的：拖的过程、落点、并组的判断都走同一段代码，但“鼠标被别的窗口抢走”“拖到一半切了前台”这类只有真鼠标才有）；Windows 10 上的边缘（改不了边线颜色，应该还有那圈灰边）；多组时的「＋」菜单（菜单是系统弹出的，脚本点不了；“点过「＋」的那一组优先”只有代码和单元测试）；拖到另一块缩放比不同的屏幕。

### UI-17 实例栏自动收起（试验，2026-11-17，需求方：“顶部实例标签太占位置了”“默认压扁变成色条，顶部相当于一个彩虹条，靠近展开”）

- **状态**：~~试验（demo），等需求方用真鼠标试过再定去留和细节。默认关~~ **2026-11-18：需求方用过后定为默认开**，开关 `mergeCompact`（设置 →「启动」→「实例栏自动收起」，只在“合并窗口”开着时出现）。
- **样子**：
  - 收起：每个实例一小段颜色，画在窗口最上面 5 像素里（那里本来只是标题栏的底色），**不出窗口的边、都一样粗**。
    当前的：实例本色，和展开后它的标签一样宽。别的：暗一些、灰一些（去掉四成彩色，再按 72% 盖在标题栏底色上），长度是标签的 55%。
    从左边起一段挨一段排，**缝都一样宽**（4 像素，和标签之间的缝一样）；所以除了第一段，色条和展开后的标签左右对不上，展开时各自滑过去、长宽。按在色条上按色条的位置算是哪个实例（`StripHit`）。
    （前一版短的那段在自己标签的位置上居中，缝有宽有窄。需求方：“间隔还不一样，长短变了间隔还是要一致，不然太难辨认”。）
    （上一版当前的 9 像素、别的 6 像素，骑在窗口上沿上。需求方：“当前实例的颜色条会变粗然后挤出边界，改成当前的颜色正常显示、非当前的暗淡灰一点就好了，没必要改粗细；要改也可以改横向的长短，被选到的宽、没选的短”。）
  - 接鼠标的那一条比看得见的色条高：窗口上沿外面 4 像素（看不见）+ 里面 5 像素，左右是整条色条再各放宽 4 像素，含段与段之间的缝。它整个是实例栏自己的窗口：
    鼠标到了上面不会变成“改窗口大小”的箭头、也拖不到窗口，只管展开。没画东西的地方留一丝看不出来的透明度（1/255）来接鼠标；这一条以外全透明、点得穿。
    （第一版“靠近”的范围伸进了标题栏。需求方：“触发展开、改窗口大小、拖窗口都混在一起了，有点难点，顶部加宽几个像素”。）
  - “铺满”时窗口占满可用区域（色条在窗口里面，上面不用让）；鼠标顶到屏幕最上面就在色条上。
  - 展开：鼠标一到色条上就展开，整条栏盖到浏览器自己那排标签页上（右上角三个窗口按钮不盖）；鼠标一离开（四周放宽 10 像素）就收。**都不等**。
    （前两版要在色条上停 0.08 / 0.06 秒才展开、离开 0.35 秒才收。需求方：“展开不够跟手，离开收缩不够快，有延迟的感觉，不是零延迟即时响应的那种”。）
    真鼠标到色条上系统会发消息给实例栏，当场展开；另有每 10 毫秒（系统实际约 16 毫秒）看一次鼠标的定时器管“离开”和兜底。＋ 的菜单开着不收。
  - 栏刚展开不到 0.4 秒就按在色条那几行上：照色条的位置算是哪个实例（人瞄的是色条，来不及看展开后的标签）。鼠标没动就直接按在收着的色条上也一样。
  - 正拖着标签、正有实例要并进来时不收。拖出去、并进来的规矩同 UI-16（“拖到另一组的栏上”按那一组展开后的位置算）。
- **过渡**（需求方：“展开有点卡卡的掉帧一样，希望是渐变展开”）：第一版是 3 帧、每帧改一次窗口大小，看着卡。现在窗口一直是展开那么大（收着时除了色条全透明，鼠标点得穿），展开 / 收起只换画面：每段色条往下长成标签（位置、圆角、颜色一起过渡），底色由透明变实并从上往下铺开，字、×、＋ 在后一半淡入。展开 150 毫秒、收起 110 毫秒，都是一开始最快（第一、二帧就走了一大半），越到后面越慢。每帧等系统合成（`DwmFlush`）再画下一帧，跟显示器刷新率走。过渡到一半鼠标又回来 / 又走了，从当前的样子当场掉头（每帧都看一眼鼠标），不等这一段放完。（前一版 240 / 180 毫秒，收起是先慢后快——鼠标走了画面半天不动，就是“有延迟”的来源之一。）实机：展开 11 帧 / 157 毫秒，收起 8 帧 / 117 毫秒，帧间隔最长 17 毫秒。
- **代码**：`tabbar.go`（`CompactRect`、`LayCompact`、`Strip`、`StripHit`、`Band`、`Reach`、`Stay`、`CarryCompact`、`FilledCompact`）、`render.go`（`Morph` 画任意一刻、`MorphRect`、`InkAlpha`、`EaseOut` / `EaseShut`）、`paint_windows.go`（`surface`、`frame`、`animate`）、`bar_windows.go`（`wantOpen`、`hoverTick`、`setOpen`、`under`、`dropRect`）。测试 `TestCompact`、`TestMorph`；`FILM=路径 go test -run TestFilm ./internal/tabbar` 把过渡的几个时刻画成一张图。诊断接口的 `trace` 里每段过渡记一行帧数和最长帧间隔。
- **证据（需求方实机，开发版）**：屏幕实拍收起是三段色条、展开盖住标签页一排且窗口按钮还在；模拟鼠标：展开、6 秒后自己收起、点标签切换、拖出去落点对、拖到另一组顶上并进去、双击空白铺满整个可用区域再还原。
- **过渡的实测**（需求方实机，60 Hz）：展开 16 帧 / 约 250 毫秒，收起 12–13 帧 / 约 190 毫秒，最长帧间隔 17–18 毫秒（没有掉帧）。
- **没验证**：真鼠标靠近展开的手感（延时、范围是拍脑袋定的）；想点浏览器标签页时会不会误触发；别的缩放比。

**补充（2026-11-18，需求方：“鼠标靠近顶部展开，切换实例点击后鼠标移开，就会把实例拽出来……按道理长按拖拽出来才对，我只是单击”）：单击不能变成拖动；按住拖要一直跟手。**
两个毛病，一个根子：程序靠系统发来的“鼠标移动 / 松手”消息来拖，可这些消息不保证到。
1. **单击被当成拖。** 点标签这一下，程序先换实例（换窗口 + 淡出，0.2～0.3 秒，这期间不处理别的消息），换完才记“开始拖了”。
   普通的一下单击，这时手早松了；排在后面的“鼠标移动”却可能比“松手”先处理，或者松手送给了别的窗口。程序以为还按着，鼠标一离开栏就把实例拖成单独一组。
   实测（真鼠标，用系统输入接口）：需求方机器上老版本“按 30 毫秒、松手后马上移开”第一下就拖出去了，松手后停 0.3 秒再移开的 6 下没出；CI 上 7 下出 1 下。
2. **按住拖，窗口半路停下。** 拖出栏以后前台窗口是浏览器不是我们，系统只在鼠标压在实例栏上时才把移动、松手发给我们；手稍快一点鼠标跑到栏外，消息就断了。
   实测（需求方机器，老版本）：按住往下拖 400 像素，窗口跟了 50 / 226 就停了，松手后程序还记着“正拖着”（之后鼠标一碰栏，窗口就跳过来）。
现在的做法（`bar_windows.go` 的 `dragWatch`，点完标签马上跑一次，之后每 10 毫秒一次，只管真鼠标）：
- 直接问系统“主键现在是不是真的按着”（`primaryDown`，系统设了左右键互换也认）。
- 没按着：收尾。还没拖出栏 → 就当只是点了一下；窗口已经在跟着走 → 按“在鼠标现在的位置松手”算（该并进别的组照并）。
- 按着：鼠标到哪儿窗口跟到哪儿，不等“鼠标移动”消息。
- “鼠标移动”消息自己说“没按着”时也一样收尾。
不认系统的“鼠标被收走了”通知当拖完：拖出栏的那一下我们自己会把“抓着鼠标”从旧栏换到新栏，旧栏照样收到这条通知——试过拿它当拖完，窗口刚出栏就不跟手了。
按住不放再拖照旧；点的是别的实例的标签时，要按住超过换实例那 0.2～0.3 秒才算拖。测试脚本模拟的拖动（`mkTest`）不受影响。
检查：
- CI（Windows 有界面的冒烟，`scripts/smoke.mjs`）：真鼠标单击四遍（两遍松手后马上移开）；按住拖出去（看窗口是不是跟到了松手的地方）、再拖回来并上。
- 需求方机器的测试副本（`/home/user/tools/realclick.ps1`、`realdrag.ps1`、`realblank.ps1`，都是真鼠标）：单击 16 遍全是只换实例；拖出 400 像素窗口正好跟了 400、
  拖回去并上、按住 0.7 秒不动再松手不算拖、抓空白处拖整个窗口 (150,120) 正好挪了这么多。
没查的：窗口铺满 / 最大化时的拖动、别的缩放比例、Windows 10、三个以上实例。
另记一个没修、也没查实的小毛病：CI 记录里见过一次鼠标停在栏最上面两像素（窗口上沿外面）时，栏连着一开一合抖了五下。猜是展开以后那一条不画东西、鼠标“漏”到了下面，待查。

### UI-18 换实例时旧画面渐变成新画面（2026-11-17，需求方：“切换实例太闪烁了，可以渐变过渡吧”）

- **为什么闪**：换实例 = 显示一个窗口、藏起另一个。系统给两个窗口各放一段出现 / 消失的动画，新窗口还要重画，中间露出后面的东西。
- **做法**（`internal/tabbar/fade_windows.go`）：换之前把屏幕上这一组现在的样子（窗口 + 实例栏）拍下来，原样盖在最上面（鼠标点得穿）；底下换窗口，这一下关掉这两个窗口的系统动画（`DWMWA_TRANSITIONS_FORCEDISABLED`，换完恢复）；再等 30 毫秒，让盖着的那一层在 160 毫秒里淡出去。合并窗口开着就有，不分是否自动收起。正拖着标签时不做（要跟手）。
- **真机上找到并修掉的**：盖着的那一层一开始是“归实例栏所有”的普通窗口，换窗口时新窗口先被提到最前面，露出一帧新画面又变回去——改成总在最上面。淡出一开始是每帧重新交一次图——改成整个窗口一个透明度，每帧只改这个数（更省事；“原来只有 30 帧”这个说法**没证实**：那个数只在开着取色采样时出现，不采样时改之前 11 帧、改之后 10 帧，差不多）。
- **证据（需求方实机）**：换实例时连续量屏幕上两个点（工具栏、网页中间）的颜色，四次都是从旧颜色单调地变到新颜色，中间没有跳到别的颜色。换窗口本身 70–110 毫秒，淡出 10 帧 / 167 毫秒（60 Hz，不掉帧）。从点下去到完全换好约 0.3 秒。
- **没验证**：窗口很大（4K 铺满）时拍一张图要多久；新窗口 30 毫秒内没画好时会看到它的旧画面再跳一下（没遇到，没法保证）。

- **补充（2026-11-17，全面实测时用连拍屏幕找到的）**：窗口挪过 / 改过大小 / 铺满过以后**头一次**换实例，会闪一帧上一次拍的画面（例：从黄色的 #3 换到 #0，中间一帧是红色的 #2），4 次里 4 次都有。
  原因：盖着的那一层是反复用的，以前分三步（摆好窗口 → 往上画 → 改成不透明），大小一变系统会带着旧图先亮一帧。
  改成图、位置、大小、透明度一次交给系统（`UpdateLayeredWindow`），然后才显示；淡出时每帧只改透明度（不重新交图，仍是 9–10 帧 / 165 毫秒）。改后同样的操作 4 次里 0 次。
  量的办法：`tools/win/cap.ps1`（后台线程每 20 毫秒左右拍一次屏幕上的一小块，去掉重复的拼成一张图），脚本不在仓库里，在工作区 `/home/user/tools/win/`。

### UI-20 最大化 / 铺满 / 还原：过渡交给系统放（2026-11-17，需求方：“把整个功能做的更原生、流畅”）

- **原来**：点浏览器的最大化 → 系统开始放最大化的动画 → 我们 0.07 秒后发现，先“还原”（系统又放一段缩回去的动画）再挪成铺满。两段动画叠在一起，连拍屏幕看到的是 0.3 秒的重影；
  窗口的位置走的是“最大化 → 缩回原来的小窗口 → 铺满”三步。双击实例栏空白处则一点动画都没有，直接跳。
- **现在**（`toggleFill`、`setPlaced`）：
  - 铺满：窗口先真的最大化（双击空白处时由我们来最大化），系统放它自己的动画；然后**一步**换成铺满的位置（`SetWindowPlacement`，两个位置只差几个像素，看不出来）。位置只走“最大化 → 铺满”，相隔约 20 毫秒。
  - 还原：从最大化一步回到原来的位置，系统放“还原”动画。双击空白处来的时候先不放动画地最大化一下再还原。
  - 发现最大化不再等每 0.25 秒一次的对账，窗口位置一变就处理。
  - 动画放着的 0.28 秒里实例栏先藏起来，放完再出现：栏是另一个窗口，进不了系统的动画，不藏的话色条先到、悬在半空等窗口。
- **为什么铺满的窗口仍然不是“最大化”的**：浏览器最大化以后标签页那一排变矮、顶上不留空，展开的实例栏就盖不准了（会压到地址栏）；普通状态的窗口样子不变。
- **证据（需求方实机，开发版，四个实例合并，真鼠标）**：点最大化 / 再点一次、双击空白处铺满 / 还原，连拍屏幕都是一段连续放大 / 缩小的画面，没有重影、没有悬空的色条；
  铺满时点标签换实例、把实例拖出去（回到原来的大小）、拖回来、按住空白处往下拖（回到原来的大小跟着鼠标）都对；最小化 / 还原、关开关再开都对。
- **没验证**：任务栏在屏幕上边 / 左边的机器（`setPlaced` 摆完会量一遍、差了补上，但没有这样的机器试）；别的缩放比例；Windows 10。

### UI-21 藏着的实例窗口跟着这一组走（2026-11-17，全面实测时量到的）

- **现象**：一组挪过地方 / 改过大小以后，重新打开其中一个实例，它的窗口先在老地方冒出来，约 0.2 秒后才被挪进这一组（量到：先出现在 2134,238，0.23 秒后到 2500,120）。
  关过再开“合并窗口”的话更明显：关的时候窗口被错开摆（每个往右下 32 像素），藏着的就一直留在错开的位置上。
- **原因**：浏览器关掉时记下的是窗口最后在哪，下次打开就先出现在那里（恢复上次的标签页时用的是它自己存的位置，偏好文件里的 `browser.window_placement` 改了也不管用，试过）。
  以前只有换到某个实例时才把它的窗口挪过来，藏着的留在上次露面的地方。
- **做法**（`align`，每次对账时顺手做）：藏着的窗口一直待在当前窗口的位置、一样大；铺满着的时候待在铺满之前的位置。异步地挪，浏览器卡住也拖不住我们。
- **没用的办法**：启动参数 `--window-position` / `--window-size`——这个实例以后开的每个新窗口（Ctrl+N、无痕）都会出现在同一个位置，叠在主窗口正上面。
- **管不到的**：实例关着的时候这一组又挪了；头一次启动的新实例（浏览器自己挑位置）。这两种仍然先出现在别处再跳过来。
- **证据（需求方实机，开发版）**：把一组从 2500,120 1100×760 挪到 2100,260 1200×780，藏着的 #2 跟到了同一个位置；关掉 #2 再开，窗口出现在 2100,251（比该在的位置高 9 像素：测试用的位置下边出了屏幕，浏览器自己往上收了一点），随后落到 2100,260。

### UI-19 “需重启”写在第一眼看得到的地方（2026-11-17，需求方：“扩展增删必须重启吗，刷新一般不就可以了；重启在节点里面，每次还得进去一层，不知道的话什么都找不到重启提示”）

- **核查：加 / 删扩展为什么要重启**。扩展是实例启动时由核心服务用命令行参数（`--load-extension`）交给内核的，内核只在启动时读这个参数；开着的实例拿不到新加的扩展，也卸不掉删了的。核心服务按“启动时交了哪些”和“现在该有哪些”比对（`markExtChangedLocked`），不一样就给这个实例标“需重启”。需求方机器上看到的这一条是对的（一小时前从文件加了一个扩展，在那之前启动的实例被标上，之后启动的没有）。
  普通 Chrome 里“装完刷新就能用”是因为商店是装进正在跑的浏览器里；我们是所有实例共用一个扩展库、启动时分发。重启只重启这一个实例，标签页由 `--restore-last-session` 恢复。
- **不重启的路（没做，要需求方点头）**：内核有调试通道的命令 `Extensions.loadUnpacked` / `Extensions.uninstall`，能给开着的浏览器装 / 卸解包扩展；条件是启动时带 `--remote-debugging-pipe` 和 `--enable-unsafe-extension-debugging`，由核心服务一直握着这条管道（管道一断浏览器就退出）。这要改每个实例的启动方式，对指纹有没有影响、fingerprint-chromium 148 认不认都没验证，所以不顺手做。
- **改了什么**：以前“需重启 + 立即重启”只在“节点与出口”里（工具栏按钮上有个 ↻ 角标，但点开找不到在哪重启）。现在：
  - 工具栏弹窗首页（头像下面、四个入口上面）：`需重启：…  立即重启`。
  - 新标签页（搜索框下面）：同样一行，点了就重启。电脑上“出口时区变了”那条红色的断网提示原来写“去重启”、点了进节点页，现在写“立即重启”、点了直接重启。
  - 扩展页（改扩展的地方）最上面：`#1、#2 开着，重启后才会用上这里的改动  全部重启`（只有一个时写“立即重启”）；先重启别的实例，自己所在的放最后。
  - 节点与出口里原来那条不变。四处用同一句话、同一个接口（`common.js` 的 `restartText`、`restartPath`）。
  - 手机的头像菜单是 app 原生画的，这次没动（手机没有“扩展有增删”这一种）。
- **顺手修（核查时发现）**：扩展换版本时旧版本的目录是当场删的，而开着的实例还在从那个目录读文件（那个实例里的扩展会当场坏掉，直到重启）。现在有实例开着就不删；没人用的目录（旧版本、移除了的扩展、装到一半的临时目录）在核心服务下次启动时清（`sweepExtDirs`；清单读不出来时不清）。“移除扩展”的注释早就写着“留到下次启动清理”，但一直没有这段清理。
- **证据**：`scripts/check.sh pages desk`（假状态 + 真页面）新增四项：弹窗首页有这一行且平时没有、点了重启当前实例；扩展页列出要重启的实例、“全部重启”发出三个请求且自己最后；新标签页有这一行、点了重启。`TestSweepExtDirs`。**没验证**：真内核里点“立即重启”后的实际效果（接口没变，以前节点页里的按钮用的就是它）。

### EXT-1 本地扩展：记住文件夹、能“重载”、改代码不用重启实例（2026-11-18，需求方：“一个路径的插件可以一直重复添加，按道理应该锁定一个路径之后插件重载，路径内更新就会更新，并且所有实例都更新，并且刷新即可生效不需要重启才对”）

- **原来错在哪**（核查到的）：manifest 里没带密钥的本地扩展，入库时**每次都新生成一把密钥**，扩展 ID 是密钥定的——
  同一个文件夹加几次，就是几个 ID 不同的“新”扩展（列表里多出一份；扩展自己存的数据是按 ID 分的，也跟着是空的）。库里也没记它是从哪个文件夹来的，没有“重载”。
- **结论**：
  - **记住路径**：从本机路径加的扩展记下路径（`GlobalExtension.Path`），扩展页那一行写“来自 <路径>”。同一个路径再“添加”一次 = 更新那一个，沿用第一次的密钥，ID 不变。
    以前加的没记路径：名字一样的本地扩展认成同一个（顺便把路径补上）；这是按名字猜的，两个不同的本地扩展重名时会认错，概率小，记在这里。源里自己带 `key` 的以它为准。
  - **重载**：那一行多一个“重载”按钮（`POST /api/extensions/{id}/reload`），重新读那个文件夹。商店来的在“更多”里是“更新到商店里现在的版本”。
    库里的目录还是 `<扩展 ID>/<版本>`；版本没变时**原地换文件**（内容不同的覆盖、多出来的删），不再整个删掉重建——开着的浏览器正指着这个目录。`.git` 不进库。
  - **不用重启就生效**：版本没变、manifest 没变（改代码的常见情况）时，核心服务记下时刻（`CodeAt`）；每个开着的实例里的伴随扩展看到“这个扩展在我启动之后换过文件”，
    用 `chrome.management` 把它**关一下再开**。实测（fingerprint-chromium 148，`--load-extension` 加载的扩展）这样浏览器会重新读后台脚本和内容脚本；扩展自己的页面本来就是每次从硬盘读。
    已经打开的网页要刷新一下才换上新的内容脚本（和在 chrome://extensions 里点“重新加载”一样）。伴随扩展为此多了 `management` 权限。
  - **还是要重启的情况**：版本号变了（目录变了），或者 manifest.json 变了（权限、内容脚本的匹配范围、名字……）。实测“关一下再开”**不会重读 manifest**

### N-4 全局出口加 HTTPS / TURN / SSTP；节点 path 默认用 edgetunnel 的 /video/ 写法（2026-11-17，需求方：“订阅地址库好像不支持 sstp，帮我加上并且优化支持 sstp”）
- 背景：用 ProxyIP 的 edgetunnel 节点，只有 Cloudflare 的网站从 ProxyIP 出去（edgetunnel 的 forwardataTCP 先直连，失败了才走 proxyip），其他网站看到的都是 Cloudflare 的 IP 和 Cloudflare 的 DNS。想让所有网站（包括 DNS 检测）都从同一个住宅出口出去，只能给节点配一个“全局”的链式代理。edgetunnel 支持的类型有 socks5、http、https、turn、sstp，例如 VPN Gate 的 SSTP（账号 vpn / vpn）。
- 做法：
  - `internal/exits`：认出 `https://`、`turn://`、`sstp://` 以及 `sstp=` 这样的写法。https、turn、sstp 可以不写端口，按 edgetunnel 的默认端口 443、3478、443；`https://用户:密码@主机` 算 HTTPS 代理，不算列表网址。
  - `RewriteChain`：全局出口默认写成 `/video/<加密串>`。加密串就是 edgetunnel 的 `base64SecretEncode`：把链式代理的 JSON 按节点的 uuid 逐字节异或（trojan 节点用 password），再做 Base64，这样 path 里不会出现明文的账号和地址。没有 uuid，或在“高级 → 全局代理的 path 写法”里选了“明文”时，写成 `/sstp://账号@主机:端口`，旧版服务端也认。
  - 改 path 写法以后会马上重载 mihomo 配置。
- 证据：`TestRewriteChain` 测了生成的串，又拿 edgetunnel 源码（2026-11-10 的 main）里的 `base64SecretDecode` 和 `/video/` 正则解回去，得到 `{"hostname":"public-vpn-1.opengw.net","password":"vpn","port":443,"type":"sstp","username":"vpn"}`，和原来一致。
- 实测（2026-11-17 23:50，需求方电脑上的开发版，用正式版的两个订阅）：导入 5 台 VPN Gate 的 SSTP（`sstp://vpn:vpn@<主机>.opengw.net:<端口>`），经 Worker 测到 4 台能通，出口分别是 KDDI、BIGLOBE、NTT、Sony 的日本宽带 IP，延迟 210 到 1400 ms；大学那台 public-vpn 超时。实例 #1 选 NTT 那台：Cloudflare 站点和普通站点看到的都是同一个 IP，时区自动设成 Asia/Tokyo，前后一致。mihomo 配置里 11 条 path 都是 `/video/`，没有明文 sstp://。
- 还剩的问题：DNS 检测（bash.ws）看到的解析器仍是 Cloudflare 日本，因为域名是 Worker 解析的，不在客户端，客户端改不了。另外每条新连接都要建一次 SSTP，首字节 1.9 秒左右；下载约 1.1 MB/s，20 MB 的文件下到 3.4 MB 连接就断了。
- 旧版 edgetunnel 不认 `/video/`，要手动切到明文。

### UI-23 手机底部黑边：手势导航时网页画到屏幕最底下（2026-11-18，分支 iter/polish，需求方：“手机的客户端底部会有黑边，不完全支持全屏”）

- **现象**：手机上网页 / 内置页面的下面总有一条和页面颜色不一样的底（深色主题下是黑的）。
- **原因**：UI-4 让整列内容按导航栏 / 手势条的高度让开底部，露出来的那条由 `BarsLayout` 涂成工具栏底色。三键导航时这样对；手势导航时手势条底下没有能点的东西，让开反而留下一条和网页颜色对不上的“黑边”。
- **做法**：
  - `MainActivity.onInsets` 读 `WindowInsets.Type.tappableElement()`（安卓 10 用 `tappableElementInsets`）的底边。为 0（手势导航）时内容列底部不再让开，GeckoView 一直画到屏幕最底下，和 Chrome 一样；三键导航和拿不到这个值的老系统照旧让开。键盘弹出时仍按键盘让开。
  - GeckoView 会把系统栏的 insets 作为 `env(safe-area-inset-*)` 交给 `viewport-fit=cover` 的页面（`GeckoView.onGlobalLayout` → `safeAreaInsetsChanged`）。内置页面都带 `viewport-fit=cover`：`ui.css` 里 `body`、抽屉、遮罩（底部表单本来就让开）按 `env(safe-area-inset-bottom)` 让开手势条；手机外壳 `#root` 的最小高度扣掉这一段，短页面不会多出滚动。
  - 普通网站：没写 `viewport-fit=cover` 的拿到的是 0，最后一行会被细细的手势条压着（手势条只画一条线，点击照样落到网页），和 Chrome 手势导航下的样子一样。
  - 原生浮层（头像菜单、三点菜单等）仍按完整的 `inBottom` 留边，不受影响。
- **防再犯**：`preview-pages.mjs` 的 safe 段加两项：模拟底部 24px 安全区，节点页滚到底内容要让开；设置页不能因此多出滚动。去掉 `ui.css` 里那行时第一项会失败（本地试过）。
- **没验证**：Kotlin 改动沙箱编译不了，靠 CI 构建；GeckoView 算给页面的底部安全区是不是正好等于手势条（而不是整个窗口的 insets）只读过源码，没在真机上看过；需求方那台 vivo V2419A 还没装这一版。
- **回退**：`onInsets` 里把 `navPad` 改回 `inBottom` 即可，CSS 的 `env()` 在不铺到底时为 0，不用动。

- **补充（2026-11-18 第 3 轮，需求方：“三键导航也尽量做到沉浸”）：三键导航时导航栏颜色跟着网页走**
  - 手机内置扩展加内容脚本 `android/ext/bars.js`：取网页最底下那一条（导航栏正上方）的背景色——从那一点往外找第一个不透明的背景，找不到用 body / 根元素的背景，再没有按页面配色方案取默认底色——用 `sendNativeMessage` 报给 app。只报颜色值，不报网页内容；滚动、改尺寸、换回前台、深浅色切换、单页应用改 class / style 时重取（有节流）。
  - `Core.kt`：颜色只记在发消息的那个会话自己的标签页上（`Tab.pageColor`，网页改不了别的页）；换页（`onLocationChange` 地址变了）清空。`MainActivity.applyBars` 显示网页时把导航栏涂成它，还没报上来（刚打开、内容脚本进不去的页）照旧用工具栏底色。
  - 手势导航时网页本来就画到最底下，这个颜色被网页盖住，不起作用。
  - **没验证**：Kotlin 靠 CI 编译；真机三键导航下的样子没看过（模拟器默认手势导航）。回退：`applyBars` 去掉 `else ->` 那一行，manifest 去掉 `bars.js`。

### UI-27 网页翻译：两端一键整页翻成中文，请求走本实例的代理

- **为什么不能用“谷歌自带的翻译”**：电脑内核是 Chromium，没有 Chrome 里那个谷歌翻译组件；手机是 GeckoView，Firefox 的本地翻译模型 GeckoView 没有提供接口。所以自己做。
- **做法**：内容脚本 `companion/ext/translate.js`（两端共用）把网页上的文字节点一段段取出（跳过代码、输入框等，最多 4000 个），成批交给翻译接口，原样写回文字节点（不注入网页脚本、不改网页全局变量，网页看不到“翻译组件”），属性里的提示文字也翻；再点一次换回原文；翻译开着时后加出来的文字（滚动加载、单页应用）接着翻。提示条在封闭影子 DOM 里。
- 接口：先用谷歌翻译的公开网页接口（`translate.googleapis.com`，`client=gtx`），不通换微软 Edge 内置翻译用的接口。
- **R-1（不暴露真实出口）**：电脑上由扩展后台去发（实例的浏览器进程整个挂在它自己的代理端口上，后台的请求也从这个实例的出口出去），后台只认这三个翻译接口的地址，内容脚本不能拿它当万能代理；手机上内容脚本自己发（手机扩展后台的请求是直连的，不能交给后台），请求带着标签页身份，由内置扩展的分流送进本实例的代理，认不出实例一律拒绝。请求都不带 Cookie、不带来源页。
- 入口：电脑工具栏菜单的翻译按钮、网页右键菜单“翻译此页 / 显示原文”、Alt+T；手机三点菜单“翻译此页”。
- **检查**：`scripts/translate-e2e.mjs`（进 `check.sh ext`）：真 Chromium + 真扩展 + 假翻译接口，看整页换成译文、请求是 CONNECT 经代理出去的、不带 Cookie 和来源页、后加的文字也翻、后台拒绝替别的地址发请求、右键菜单有这一项。
- **没验证**：手机真机；真谷歌接口在需求方网络里经各出口能不能用（被限流时换微软）。回退：两端 manifest 去掉 `translate.js`、菜单去掉那一项。

### M-6 默认邮箱 + 默认密码：注册、登录页自动填，只填不提交

- 设置首页两行：默认邮箱、默认密码，各填一次。默认邮箱和默认密码一样只存在加密的密码库里（`vault.bin`），不进明文配置；`/api/state` 只给邮箱（设置页要显示），密码只给“设没设”。`PUT /api/vault/default` 的 `email`、`password` 各自可选。不像邮箱的不收（`LooksEmail`，有 Go 测试）。

### N-6 入口优选：后台定时测速，按小时记，自动换到当前时段最好的入口（需求方：“优选IP决定起步上限，反代proxyip决定下限。先决条件必须优选IP足够好。”）

- **以前**：入口自动 = 挑延迟最低的，测一次就定下来；当前的还能用就不换。需求方观察到：IPv6 的优选 IP 常常更快；同一个 IP 白天和晚上速度不一样；“入口 IP 似乎对整体没有特别的影响”——因为只看延迟，挑出来的不一定是下载快的。
- **怎么打分**（`internal/core/tunescore.go`，纯函数，有测试）：0–100 分，下载占 70 分（按对数，500 Mbps 封顶；起初是 100 Mbps，需求方电脑上实测好几个入口在 100 ~ 230 Mbps、全成了满分，改成 500），延迟占 30 分（50 ms 满分，800 ms 以上 0 分）。速度是“上限”所以权重大；延迟影响打开网页的第一下，也算。没测过下载的只有延迟分。理由里地址写成 IPv4 / IPv6 / 域名。
- **按小时记**：每个入口（地址:端口）一天 24 格，每格存下载峰值和延迟的滑动平均（新一次占 0.4，越近的天越算数）、测了几次、连续失败几次；超过 10 天的格子不算。估计“现在这个小时”的速度：本小时有记录用本小时；没有用前后一小时；再没有用全天平均打九折；本小时连续失败两次算 0。记录在 `state/tune.json`，不在任何订阅里、3 天没测过的删掉。
- **什么时候测、测谁、花多少流量**（`internal/core/tune.go`）：
  - 只有“有开着的实例在用这个订阅、入口是自动”时才测；入口手动、实例没开都不测。核心服务起来 3 分钟后第一轮，之后每个订阅最多一小时一轮；有实例正在大量下载（下行 > 1.5 MB/s）时这一轮往后推。界面上“立即优选”也能手动来一轮。
  - 一轮：全部入口测延迟（每个一个小请求，和“测速”第一步一样）→ 挑最多 5 个测下载：正在用的先测（要知道现在有多快才能比），再按分数挑 IPv4、IPv6 各最多 2 个（两种都测），留 1 个给这个小时还没测过的（按延迟），让没测过的也有机会。
  - 每个地址最多下 8 MB（手机 4 MB）、最多 4 秒（`cfprobe.DownloadCap`，向测速端点只要这么多字节）；每天总量上限电脑 300 MB、手机 100 MB，用完当天只测延迟。
- **什么时候换、换到哪**：只在**同一个出口国家**里挑（入口换了国家，普通网站看到的出口也跟着换国家，那就不是“换个更快的入口”了；出口国家没变，时区、语言、“需重启”都不受影响，见 A-12）；新的要有下载记录、分数比现在的高 15%（至少 8 分）才换，免得来回跳；现在的不通了直接换。自动选线（`pickEntry`）也改成按分数比（没有下载记录时就是按延迟，和以前一样）。
- **换的时候不断开**：不走 `refresh` 的“先断流、关连接、再确认出口”，只改实例出站的入口地址、重载 mihomo 配置、重新选上；mihomo 重载不关已经建好的连接（`internal/proxy/reload_keep_test.go` 用真 mihomo v1.19.34 验证：下载到一半换入口，老连接完整收完，新连接走新入口；进 `check.sh ext`）。换完经探测通道确认一次：不通，或出口国家变了（本不该变），立刻换回去。换成功在面板上提示一次“已换到这个时段更快的入口”。
- **界面**（`panel.js`，两端共用）：节点页“入口 优选 IP”下面，入口自动时多一行“当前时段最佳”：哪个 IP（国旗、写全的地址，正在用就写“正在用”）、理由（IPv4 / IPv6、几点、下载多少、延迟多少、比现在用的快多少）；悬停写什么时候测、今天用了多少流量 / 上限、上一轮和下一轮时间、换的时候不断开。点这一行进入口列表：多一个“本时段”排序（默认），最佳那一行有“本时段最佳”标签，悬停写本时段分数和依据；顶上“立即优选”按钮。入口手动时不显示这一行。
- **检查**：Go 测试 `tune_test.go`（打分、按小时估计、该不该换、这一轮测谁、按分数选入口；整轮用两个假入口——一快一慢——跑一遍：都测、按当前小时记、用量在上限内、换到快的、没断流、界面数据对、落盘、用量到上限不再测下载、确认没通过换回去；入口手动不算）、`reload_keep_test.go`（真 mihomo）；页面检查 `tune` 段（两种宽度：“当前时段最佳”的内容和悬停、不溢出、点进入口列表按本时段排、最佳标签、“立即优选”调接口；入口手动不显示）、`desk` 段一项（电脑弹窗）。
- **没验证**：需求方真实网络里的效果（IPv6 是不是真的更快、白天晚上差多少，要跑几天才有完整的 24 小时记录）；手机上的流量上限是否合适；测速端点对单次下载大小的限制以后会不会变（变了返回 403，这一轮记为失败）。
- **回退**：`setup.go` 去掉启动 `tuneLoop` 那一行就不再后台测、不再自动换；`entryCandsLocked` 去掉打分就回到只比延迟。

## iter/polish 第 4 轮（2026-11-18：纯净度 / CF 风险照 ippure.com；在需求方电脑的开发版上把第 3 轮的东西实测一遍）

### N-7 纯净度和 CF 风险：照 ippure.com 的两个系数，界面上写明哪头好、数从哪来

- **ippure.com 上是什么**：两个都是“风险系数”，0–100，**越低越好**，同一条色带（≤15 极度纯净、≤25 纯净、≤40 中性、≤50 轻度风险、≤70 中度风险、其余极度风险）。
  - IPPure 系数：这个 IP 本身干不干净（风险库 + 蜜罐，随时间衰减；IPv6 不算）。
  - Cloudflare 系数 = 100 − Cloudflare Bot Score：Cloudflare 觉得“这个浏览器 + 这条出口”多像机器人。Cloudflare 只告诉你**当前来访的这个 IP** 的分，查不了别的 IP。
- **我们怎么取**：
  - 纯净度仍是“越高越干净”（界面上一直是这个方向，圆环越满越好）：**纯净度 = 100 − IPPure 系数**。核心服务经每个实例自己的出口问一次 `my.ippure.com/v1/info`（公开接口，回来访 IP 的 `fraudScore`），24 小时内不再问，问不到 10 分钟后再试（`internal/core/ippure.go`）。问不到的 IP（直连的、IPv6、普网那一路）照旧用 `ip.net.coffee` 的分。
  - CF 风险只能实测：用户在实例里点“实测 / 重测”，打开 `https://ippure.com/cloudflare`，内容脚本 `companion/ext/ippure.js`（两端共用）把页面上的“检测对象 IP + 风险指数”读出来交给核心服务（`POST /api/ipq/cf`）。只收 0–100、IP 得是报上来的那个实例当前的出口、实例代理开着。**不在后台偷偷开页面，不伪造 ippure 那些带签名的接口。**
  - 以前的“CF 信誉”（按 Cloudflare 路上有没有被拦猜的好 / 一般 / 差）去掉，换成这个数；CF 那一路不通写“不可达”。
- **界面**（`common.js` 的 `pureInfo`、`cfRisk`，各页面只管摆）：
  - 节点页当前出口卡：圆环是纯净度；下面两行——“纯净度 29 · 极度风险”，小字“= 100 − IPPure 系数 71。ippure.com 上显示 71%（极度风险），那个数越低越干净”；“CF 风险 85 · 极度风险 [重测]”，小字“Cloudflare 觉得这个浏览器 + 这条出口多像机器人，越低越好。2 分钟前在 ippure.com 实测”。没测过是“实测”。
  - 新标签页“伪装概况”三个圆环各带一行方向：伪装度“越高越好”、纯净度“越高越干净”、CF 风险“越低越好”；CF 没测过那一格是“未测 · 点此实测”。
  - 工具栏小窗：纯净度圆环 + “CF 85 / CF 未测 / CF 不可达”。诊断页：出口纯净度、CF 风险两行。高级设置里那个开关的说明写了数从哪来、关掉连 CF 风险也不记。
- **检查**：Go 测试 `ippure_test.go`；页面检查四项（`preview-pages.mjs`）；`ippure.js` 对着真网站跑过（无头 Chromium）。
- **实测**（需求方电脑开发版，实例 #1，VPN Gate 出口 `210.138.37.53`）：IPPure 系数 71 → 纯净度 29；点节点页“重测”在本实例开出 `ippure.com/cloudflare`，页面写“风险指数 85 / 100”，几秒后节点页、新标签页、工具栏小窗、诊断页都是 85。IPv6 出口 `my.ippure.com` 不给分，照旧显示 `ip.net.coffee` 的 98。
- **没验证**：手机真机（内容脚本同一份，桥接路径只过了页面检查）。`my.ippure.com/v1/info` 文档写着“测试阶段，可能会变”——变了的话纯净度退回 `ip.net.coffee`，不会报错。
- **回退**：`ipqEnsure` 里去掉 `ippureEnsure` 那一行，纯净度回到只用 `ip.net.coffee`；两端 manifest 去掉 `ippure.js`，CF 风险就永远“未测”。

### EXT-2 伴随扩展更新后，老实例的后台脚本要跟着换：文件名跟着版本号走，装好就接手

- **实测到的问题**（2026-11-18，需求方电脑开发版，查 N-7 时发现“页面读到了数、后台就是不收”）：四个测试实例的 manifest 版本号是新的，**跑着的后台脚本却是 11-17 登记的那一份**（#0、#3 是 11-14 的内容，#1、#2 是 11-17 上午的），之后三次更新加在后台里的东西——网页翻译、向导的快捷键、CF 风险——在这些实例里都不生效。安装版同理：资料目录建得早的实例，后台一直是当时那一版。
- **原因**（`scripts/sw-upgrade-e2e.mjs` 把两条都做成对照，哪天内核行为变了对照会先报警告）：
  - 甲：内核按“后台脚本的地址没变”认定它没变。以前只改 manifest 版本号（`companion.Version()` 的注释以为这样就够）——不够。
  - 乙：地址变了内核才重装，但新后台装好后是“等待中”，要等扩展自己的页面全关掉才换上。实例启动时总会恢复出一个新标签页（是扩展页面），于是更新后**头一次启动里后台谁也不在**：扩展页面、网页发来的消息没人收，再启动一次才好。
- **做法**：

### N-8 地址库按“组”来：一个列表网址是一条，单个 IP 归“独立 IP”

- **需求**（2026-11-18）：ProxyIP / 优选 IP 的来源现在都是一个个 IP。接口的 txt、csv 应该是一条，像域名那样，写有多少个、上一次什么时候更新，方便编辑和更新；单个的 IP 归到“独立 IP”组。
- **以前**：导入框里写列表网址，核心服务当场拉一次，把里面的地址一条条摊进地址库，之后和这个网址再没关系——列表换了内容只能一条条删掉重新导入，地址库里是几十上百行 IP。
- **现在**（数据）：`ExitEntry.Source = "list"` 是一条“列表源”，和域名、VPN Gate 源同一套机制（`Expand`、`Resolved`、`RefreshHours`、定时刷新 `refreshExits`）：
  - `Value` 是网址，`Label` 是名字（默认“主机名 · 文件名”），`Resolved` 是列表里的每个地址，`Labels` 是各地址在列表里带的备注（`#HK` 之类）。
  - 列表里可以夹全局出口：那一项写成 `socks5://账号@主机:端口`，类型按各项自己的来（`exitRef`）。出口 id 还是“条目|项”。
  - `GoodAt` = 上一次**成功**更新的时间（域名、VPN Gate 也记）。`ResolvedAt` 是上一次“试过”的时间，失败也记——界面上写的“多久前更新”用 `GoodAt`，不会把一次失败说成更新过。
  - 拉不到、返回网页、里面没有地址：保留上一次的结果，原因写在这一条下面。
  - 每个列表最多留 500 个地址；一次导入最多 5 个网址（和以前一样）。
- **内容格式**（`exits.ParseList`）：一行一个 / `IP:端口#备注` / 逗号分隔（原来就认）；**带表头的 CSV**（有 IP 列，再有端口列或地区列时按列取——以前端口列会丢，全当 443）；**JSON**（对象里的 `ip` / `address` + `port` + `country` 之类，或者字符串数组）。测速工具导出的 `IP 地址,已发送,…` 照旧。
- **拉取途径**：先直连和本机代理，不通再借浏览器的节点（和 VPN Gate 列表一样）。列表常放在 `raw.githubusercontent.com`，有的网络直连打不开。
- **老数据怎么办**：以前摊开的 IP 已经不知道来自哪个网址，升级后它们都在“独立 IP”里。把网址再导入一次：建出列表，地址库里和列表重复的零散条目**并进列表**（条目删掉，选着它的实例改成选列表里的那一项，手写的备注带过去；探测结果按地址记，不受影响）。只在导入和改网址时并，定时刷新不并（手动加的 IP 不会因为哪天出现在列表里就被悄悄收走）。
- **独立 IP** 不是一条数据，是界面上的归类：手动加的、单个 IP 的 ProxyIP（`isLoose`；域名、源、全局代理不算）。`PUT /api/exits/loose {text}`：把这一组整个换成一段文本里写的——没写的删掉，写着的留下（id 不变，实例的选择不动），新写的加上；文本里别的东西（域名、网址、全局代理）照导入处理。
- **接口**：`POST /api/exits` 的回答多了 `lists`、`listAddrs`、`updated`、`absorbed`；`PATCH /api/exits/{id}` 多了 `url`（先拉新网址，拉到了才换）；`POST /api/exits/{id}/resolve` 对列表就是“立即更新”；只改备注不再顺带重新解析。
- **界面**（`pages.js`，电脑和手机同一份）：
  - 地址库一行一组：列表（名字、“列表”标签、各国几个、`N 个地址 · M 个通 · 多久前更新 · 每几小时更新`、失败原因）、域名（原样，多了“多久前更新”）、VPN Gate、全局代理、最后一行“独立 IP”。标题右边写“几组 · 多少个地址”。
  - 点列表：查看地址 / 立即更新 / 修改网址 / 改名 / 自动更新的间隔 / 删除。“查看”进子页 `exits/g-<id>`：顶上一行是名字、网址和更新情况（点它改网址），下面每个地址一行，右上角闪电测全部、刷新立即更新。域名的菜单也多了“查看 N 个地址”，进同一种子页。

### UI-28 电脑版加“运行情况”页：自己把账算清，不指望任务管理器

**问题**：Windows 任务管理器里，实例的进程一律叫 Chromium（内核程序自带的名字），一个实例十来个，散着排，看不出哪个是哪个实例的，也没有合计。Edge 在那里是一行、能展开。

**定的做法**

- 左边导航“实例”下面加一页“运行情况”（`#usage`）。最上面一块是总数：内存、处理器、进程数、开着的实例、窗口、标签页，外加一条内存分布条（每个实例一段，用实例自己的颜色，最后灰的一段是后台）。
- 下面每个开着的实例一行，按内存从多到少：几个进程、几个窗口几个标签页、记住几个账号；右边是内存和处理器。点开看明细：
  - 进程按用途分：主进程 / 网页 / 扩展 / 图形 / 网络等服务 / 其它（从命令行的 `--type=` 认）。
  - 窗口和标签页：按窗口列出每个标签页的标题和主机名，标出当前、固定、休眠、出声。无痕窗口只说有几个，不列内容。
  - 账号：记住了账号的站点、留有 Cookie 的站点（本来就在 `/api/state` 里）。出口和此刻的网速。
  - 三个按钮：切到这个实例、设置、关闭。
- “后台”一组：核心服务、代理内核（连同 Windows 给它配的 conhost）各一行。没开的实例列在最后（不占内存，带账号数和“打开”）。
- 数怎么来：核心服务知道每个实例内核的进程号，顺着父子关系数（`internal/procs` 的 `Take().Tree(pid)`，只认不比父进程早出生的孩子，防进程号被重用认错亲）。内存取“专用工作集”，和任务管理器“内存”那一列同一个口径；处理器是两次取样相减，按整机算。窗口和标签页由伴随扩展报（`POST /api/tabs`，只报标题和主机名，不报完整网址；核心服务只放内存里，不落盘；实例重开后上一回报的不算数）。
- 只在这一页开着、窗口看得见时每 2 秒问一次 `GET /api/usage`，离开就停；平时不占资源。

- 发版前补的几处（2026-11-18，“考虑周全一点”）：
  - 两个窗口同时开着这一页：不到一秒前刚算过就给那一份。不然两次取样挨得太近，处理器占用在 0 和实际值之间来回跳。
  - 标签页上报从“每次变化都重新计时 1.5 秒”改成“约好了一次就不再往后推”：有的网页每秒改一次标题，原来的写法永远报不出去。
  - 内存取法三条路从准到粗：`GetProcessMemoryInfo` 新结构（Windows 11 22H2 起）→ `NtQueryInformationProcess(ProcessVmCounters)`（Windows 10 起）→ 整个工作集。落到第三条时接口带 `rough`，页脚照实写“会比任务管理器大一些”。
  - 鼠标按着的时候不重画（免得按下和松开落在两个元素上，点了没反应）。关掉的实例报过的标签页不留。接口带 `took`（算一遍用了多少毫秒）。
  - 在需求方电脑上量过：全机 614 个进程、自己名下 18 个时，算一遍 20 毫秒上下。

**没做的**：让任务管理器把这些进程合成一组、改名字。名字写在内核程序（第三方的 fingerprint-chromium）自己的资源里，要改就得改它的文件；为什么在需求方电脑上不成组也没查清（猜是合并窗口时没轮到的窗口藏着，系统只给有可见窗口的程序成组——没验证）。手机上没有这一页（一个内核进程管全部实例，分不开）。

**核对**

- `internal/procs` 的 `TestTreeAndGet`、`internal/core` 的 `TestUsage` / `TestProcKind`（Windows 上也在 CI 里跑 procs 那个）。
- 页面检查 desk 段新增 14 项（总数、排序、刷新后有处理器占用、展开明细、长标题不撑破、窄窗口、离开就不问）；冒烟新增 3 项（真内核下数得出进程和内存、扩展报了标签页、合计对）。
- 需求方电脑开发版（4 个测试实例）：进程数和系统自己数的一样（11 / 7 / 8 / 8），内存和系统的专用工作集相差几兆到几十兆（不是同一秒取的）。截图 `shots/ui28/usage-pc.png`。

**怎么撤**：导航里去掉 `usage` 那一项、删 `companion/ext/usage.js` 和 `internal/core/usage.go`；`background.js` 里 `reportTabs` 那一段删掉。`internal/procs` 新加的 `Tree` / `Get` 留着不碍事。

### D-6 开着合并窗口时“退出”会卡死：放窗口的时候不能握着锁等管栏的线程

- **怎么发现的**：UI-28 发版前在需求方电脑的开发版上试，让核心服务退出（`POST /api/quit`），8 秒后它还活着；连着两次都这样。加了一个调试接口 `GET /api/debug/stacks`（各协程停在哪）抓到现场：
  - 退出的那一路停在 `tabbar.Release()` 里的 `ShowWindow(实例栏, 隐藏)`——它握着 `mu`，在等管栏的线程来办这件事；
  - 管栏的线程停在定时对账 `sync()` → `snapshot()` 的 `mu.Lock()`——它在等 `mu`。
  - 两边互相等，永远不动。管栏的线程每 10 毫秒、250 毫秒各拿一次 `mu`，`Release` 握着 `mu` 的时间只要长一点（要放的藏着的窗口多）就撞上。
- **后果**（这段写法至少从 v0.1.120 起就是这样——提交 `ad0301c`“合并窗口可以有好几组”；更早的版本没去查。开着合并窗口、有藏着的窗口时才容易撞上）：核心服务退不掉；藏着的实例窗口放不出来；实例没有被正常关闭。升级时安装程序等 20 秒等不到它退，0.1.179 及以前的安装程序接着就是“无法打开要写入的文件 masktab.exe”——**D-5 那次“装不上”很可能也有这个原因**（当时那个退不掉的旧服务正是 0.1.120、开着合并窗口；但当时只查到锁文件不指着它，没有抓现场，证实不了）。0.1.183 起安装程序会按路径把它结束，能装上，但实例是被硬结束的。
- **改法**：`Release` 握着 `mu` 只把“不再管”记上、把要办的窗口抄出来、清空名单，放开 `mu` 再去显示 / 隐藏；办完再看一眼名单（管栏的线程可能正对到一半又藏了一个），有就再放。整个过程最多等 3 秒，别的程序的窗口卡住时不拖住退出。
- **顺带**：上次核心服务被结束后留下的内核进程，原来只在“自动开窗口”的启动方式里清（`Start()`）；带 `-no-open` 启动时不清，再开同一个实例窗口会开到没人管的旧进程里。拿出来成 `CleanLeftovers()`，两种启动都叫。
- **核对**
  - `internal/tabbar` 的 `TestReleaseDoesNotDeadlock`（只在 Windows 上跑，CI 的 Windows 那一路加上了）：一个线程管几个窗口、每 5 毫秒拿一次 `mu`，连做 20 遍 `Release`。需求方电脑上：改之前的 `Release` 第 13 遍卡死，改之后 20 遍 0.3 秒过。
  - 需求方电脑开发版，两个实例（一个藏着）：改之前退出 2 次卡 2 次；改之后 3 次都在 1 秒内退干净，内核进程一个不剩。
  - 结束核心服务、留下两个实例的 16 个内核进程，再带 `-no-open` 启动：日志里“清理上次遗留的内核进程”两条，内核进程清零。
- **没验证**：安装版上从 0.1.179 升上来的那一次（旧的那个服务还带着这个毛病，可能要等 20 秒、实例被硬结束）。
- **怎么撤**：`git show 29d9ba0:internal/tabbar/bar_windows.go` 里的 `Release`（不建议：就是会卡死的那一版）。
